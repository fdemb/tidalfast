# Playback

`src/audio` plays FLAC at any rate and depth: TIDAL's `LOSSLESS` as one FLAC file, and `HI_RES_LOSSLESS` (up to 24-bit 192 kHz) as DASH. `src/app/player.odin` connects it to the queue, the player bar and the shell.

## Getting a stream

`tidal.resolve_stream(session, track_id, quality)` asks v1 `tracks/{id}/playbackinfopostpaywall` with `playbackmode=STREAM`, `assetpresentation=FULL` and an `audioquality`. The app calls it through `resolve_stream_flac`. A PKCE login asks for `HI_RES_LOSSLESS` first, and asks again for `LOSSLESS` if TIDAL refuses that tier: a 403, no stream at that tier, an encrypted one, or a lossy one in its place. That's riptide's rule; it found a 403 means the account isn't entitled to the tier, and that a `HI_RES_LOSSLESS` answer can carry AAC. TIDAL answers a track it won't play, such as one pulled from the catalog, with a 401 and a 4xxx `subStatus` (4005, "Asset is not ready for playback"). `resolve_stream` turns that into `Stream_Not_Available`, so it asks for `LOSSLESS` too, and if that fails the player skips the track. Left as a plain 401 it would sign the user out. Any other 401, a 429 or a 5xx isn't a refusal of the tier and fails the track as it is. The device-code login asks for `LOSSLESS` only. Either tier may come as either manifest: mare-player found the Android client gets DASH for `LOSSLESS` too. The answer carries one of two manifests:

- BTS (`application/vnd.tidal.bts`): base64 JSON with `mimeType` (`audio/flac`), `codecs`, `encryptionType` and `urls`. `resolve_stream` returns the first URL.
- DASH (`application/dash+xml`): a base64 MPD with one `Representation` (`codecs="flac"`, `mimeType="audio/mp4"`) and a `SegmentTemplate` with absolute `initialization` and `media` URLs (`$Number$` from `startNumber`, a token in the query) and a `SegmentTimeline`. `dash_info_from_mpd` expands the timeline (`t`, `d`, `r` repeat counts, `r="-1"` up to the next `t` or the end of the period) into segments with their start and length in `timescale` units. `resolve_stream` returns the initialization URL, the segments and the timescale. A manifest that asks for more than 200,000 segments, a repeat count that wraps around, a URL over 16 KB (a `%0Nd` width or a long `RepresentationID` can make one) or more than 32 MB of URLs in all is refused before the segments are made. `core:encoding/xml` would print its parse errors with the text around them, which can hold the stream's URLs, so the parser is given a handler that prints nothing.

Both come with the sample rate and bit depth and the ReplayGain fields `trackReplayGain`, `trackPeakAmplitude`, `albumReplayGain` and `albumPeakAmplitude`, the names tidalapi, riptide and the other reference clients read. It refuses encrypted streams (an `encryptionType` other than `NONE`, or a `ContentProtection` in the MPD) and anything that isn't FLAC. A non-FLAC manifest fails with `Lossy_Stream` and the codec as its detail. The player bar then says "TIDAL sent AAC for this login. Log in with TIDAL again for lossless." and playback stops on that track rather than failing through the queue, since every track comes the same way for that login. There's no AAC decoder. A missing gain is 0 dB and a missing peak 1.0. A track without album gain uses its track gain for both.

Resolving runs as a `Stream` job on the data workers. A stream that doesn't resolve is logged on stderr with the track id, the error kind, the HTTP status, TIDAL's `subStatus` if the body had a numeric one, and for `Lossy_Stream` the manifest's codec:

```
app: stream for track 900101 failed: Lossy_Stream, codec MP4A
app: stream for track 900101 at HI_RES_LOSSLESS failed, asking for LOSSLESS: Http, HTTP 403, subStatus 4005
```

What the server said (`userMessage`, `errors[].detail`, or the start of a body that isn't JSON) never goes to a log. A 500 from a CDN can echo a signed URL, and an error body can hold anything. That text stays in the error's detail for the player bar. `tidal.error_summary` builds the log line from the structured fields alone, and a codec or quality name gets in only if it's on a known list (`tidal.codec_name`, `tidal.quality_name`), so a manifest with a URL for a codec logs `codec unknown`. `src/tidal` follows the same rule on its own `log` calls: a failed login logs its HTTP status, a backoff its status and length, and an error response no body at all. Nothing logs a token, a stream URL, or the pasted PKCE address with its one-time code.

 Stream URLs expire, so when a download fails with a 4xx the app resolves the track once more and carries on from where it was.

## Threads and buffers

```
fetch thread per track slot --bytes--> Stream window --> decode thread --float frames--> Pcm_Ring --> audio callback --> device
```

- **Fetch.** Each of the two track slots, current and next, has a thread that downloads the file with curl into a 3 MB window: about 17 s of 16/44.1 FLAC and 5 s of 24/192, with the ring's 3 s after it. A DASH track is the initialization segment and then each media segment, fetched one after another into the same window as one run of bytes; see DASH below. The window slides forward as the decoder reads and keeps 256 KB behind the read position for short seeks back, or a quarter of the window when it is smaller than 1 MB, so most of a small window stays free for the bytes ahead. A read takes the bytes that are there and waits only for the rest, so a read longer than the window still completes. Each request is an HTTP `Range` from where the window ends. When the window is full the thread blocks on a condition variable, so a paused track holds a connection and uses no CPU. If the server closes the connection, the thread resumes from where it got to. After 5 failures in a row, or a 4xx, the track fails. The window is a mapping of its own. When the slot's stream is cleared, by a stop, another track or none, its pages go back to the system and stop counting against the app until bytes arrive again. macOS gets `MADV_FREE_REUSABLE` and `MADV_FREE_REUSE` before the next write. Linux gets `MADV_DONTNEED`, after which the pages read as zeros and a write takes a fresh one. It was 8 MB of heap that stayed dirty after playback stopped: after the mock's hi-res album played out, 5.9 MB of it was still counted, and none is now.
- **Decode.** One thread owns the slots and the device. It feeds dr_flac (`drflac.open` with our own read, seek and tell callbacks) `fLaC` and STREAMINFO, flagged as the last block, and then the file from whatever frame a seek started at, applies the track's ReplayGain and writes float frames into the ring. The header is read whole before that, and a track whose header passes 16 MB fails. The other blocks, cover art among them, are not kept. Commands, arriving bytes and the device listeners wake it through a `Wake`, a semaphore whose posts coalesce. While one is pending, more add nothing, so a window filling chunk by chunk wakes the thread once. One wake-up can stand for several kinds of news, so the thread looks at everything again before it sleeps. A read waiting for bytes sleeps on the `Wake` with no timeout, since the fetch thread posts every change the read looks at. Nothing wakes it when the ring has room: while the device runs it also wakes on a timer, every 250 ms or sooner if a quarter of the ring (`LOW_WATER`) would play in less, and tops the ring up. While nothing plays (paused, stopped, or the queue ended) the device is stopped and it waits on the `Wake` with no timeout.
- **Ring.** `Pcm_Ring` is a single-producer, single-consumer ring of 131,072 frames (3 s at 44.1 kHz) with atomic read and write positions. The decode thread drops everything not yet played by storing a flush position, which the callback skips to on its next call, so the writer never touches the reader's position. A queue of marks next to it says which track or seek starts at which ring position. The callback adopts each mark once it has read past it, so the status describes the frame being played.
- **Callback.** The output's own thread calls it: CoreAudio's, PipeWire's, or the player's render thread on Windows and for the null device (see Output). It copies frames out, ramps the volume over one buffer, adopts marks and publishes the current mark and position. It never locks, allocates, logs, waits or makes a system call, and it doesn't use the Odin context. For the seek latency log it reads `clock_ticks` (`src/audio/clock_darwin.odin`), which is `mach_absolute_time` and reads the commpage. The mark's serial, seek id and end flag and the position go out in their own atomics under a sequence count that is odd while they change, and `status` reads them again if the count was odd or moved, so it never pairs one track's or seek's mark with another's position.
- **Main thread.** The app sends commands (`play`, `stop`, `seek`, `set_next`, `set_paused`) under a mutex that the decode thread holds only to copy them, and reads a `Status` snapshot each frame. Neither waits on the network or the device. The decode thread wakes the UI when the status changes, and four times a second while playing for the progress bar.

## Queue and gapless

Double-clicking a row copies the open list into the queue and plays from that row. The rows after it follow. Each new queue gets a generation, and a preloaded track is reused only if its generation, row and track id all match, so a row of a new list never plays bytes preloaded for the old one. The play button and the toggle media command start the selected row (or the first) when nothing is loaded, start the queue again from the top once it has played out, and otherwise pause or resume. Signing out, or TIDAL ending the session, stops the player and clears the queue and Now Playing. The volume stays. It is saved in the settings file when the slider is let go. Next and previous move through the queue and skip rows without a track id. Previous restarts the track instead once it has played 3 seconds. The queue follows the list while its pages load, also after another list opens.

Play next and Add to queue in the track menu, from any list, add a track to the queue without replacing it. The queue copies the row into its own arena (title, artist, album, cover, length, ids), since the row's list may close, and keeps it as an extra, after the list's items. Each extra has an anchor: the item it plays after in play order, the current track for Play next, or none for Add to queue. The play order is the list's order with each extra spliced in right after its anchor, together with whatever hangs from it, the newest first, so a second Play next goes before the first. Extras without an anchor go at the end, in the order they were added. An insert puts the extra into the order where it belongs without reshuffling the rest. If the player is already audibly on the preloaded next track, Play next goes after that one. If the insert changes which track is next, the preloaded next track is dropped as for a change of shuffle or repeat, and the player asks for the new one. With nothing queued, either one starts a queue of just that track and plays it; so does an insert while the current track stopped on a failure. A queue that has played out goes on to a track added after it. The status bar says "Playing … next" or "Added … to the queue". The extras stay while the list's pages arrive and when its rows move: they're taken out, the list's items are brought up to date, and they're put back with their anchors following the items they name. While an extra plays, no row of the list is lit, even when the list holds the same track.

About 30 seconds before the current track ends, or once all of it has downloaded, the player asks for the next track. The app resolves it and hands it over with `set_next`, and its fetch thread starts downloading. When the current track's decoder runs out, the decode thread writes the next track's first frames into the ring right after the last ones, with a mark between them, so the device sees one unbroken stream. When the mark plays, the queue moves on. If the next track's stream fails to resolve, the app remembers it by queue generation, row and track id and doesn't ask for it again while the current track plays, even though the player keeps asking for a next track. When the current track ends that track becomes current, gets one more try, and if it fails again the player bar says why and the queue skips on. A new queue forgets it. If the next track has a different sample rate or channel count (or bit depth, in bit-perfect mode), the decode thread lets the ring play out and reopens the device, which leaves a short gap. While it waits it wakes as soon as the ring should be empty instead of every 250 ms, so the gap is the device's re-clock and little else (see Bit-perfect output).

## Sleep timer

The player bar's sleep timer (`src/app/sleep.odin`, [UI](ui.md#sleep-timer)) is `Playback.sleep`, so `playback_stop`, and with it sign-out, clears it, and it isn't saved. Pausing by hand leaves it set.

A timed one keeps its deadline on the frame clock, the shell's monotonic clock, which `sleep_update` compares at the top of every library frame. It fires in the first frame at or after the deadline, however late that frame is, as after the process was stopped. The macOS and Linux clocks don't count time the computer sleeps, so a timer counts the time the computer was awake, which is the time music could have played. If nothing plays when it fires, it only clears. Otherwise the volume fades out over 3 s (`SLEEP_FADE`) and playback pauses as the pause button pauses it, so Now Playing and MPRIS see an ordinary pause. The fade steps the player's volume down 30 times a second with `audio.set_volume`, which the callback already ramps over one buffer, so it doesn't click; the slider and the saved volume don't move. The player's volume goes back to the slider's once the pause has reached the player (the status says Paused), or at once if play is pressed first, so resuming isn't silent. Muted, or with bit-perfect output, which skips the volume, there's nothing to fade and it pauses at once. The queue stays where it paused.

End of track is in `playback_observe`. While it's set, the next track isn't preloaded, and one already preloaded is dropped (`sleep_hold_next`), so the current track ends instead of going on gaplessly. When it ends, the queue moves to the next track paused at its start, and play goes on from there; on the queue's last track the queue ends as usual. In a track's last seconds the decoder may already have written the next track's first frames into the ring after the current track's last. Setting End of track then seeks the current track to where it is, which takes the next track back out of the ring at the cost of a short dropout, and drops it once the seek has landed. If the player still reaches the next track, as when the timer is set in the same moment, it pauses there and goes back to its start.

`TIDALFAST_SLEEP_TEST=<seconds>` sets a timed timer of that many seconds at the first frame, for checking a timed stop headless.

## Shuffle and repeat

The queue plays its items in an order, `Playback.order`: each item once, in list order, or with shuffle on, the track that starts the queue first and the rest shuffled (`audio.queue_order`). Every "what's next" goes through it, so next, previous, the preloaded next track and the end of the queue all follow the shuffle. Turning shuffle on mid-track shuffles what comes after the current track, and turning it off goes on in list order from it. While the list's pages load, each new copy of it keeps the order up to the current track and the preloaded next one, by track id, and shuffles the rest again.

Shuffle only moves the list's items; the extras keep hanging from their anchors, so a pass plays each of them once and repeat all goes round with them in place. Where shuffle wants an extra first (the current track when it's turned on), the list item the extra hangs from goes first instead, so a Play next track that plays when shuffle changes stays right after the track it was queued after.

Repeat goes off, all, one. On repeat all, the end of the order goes round to its start; a shuffled queue goes round in the same order. On repeat one, the current track is preloaded as its own next track, so it loops gaplessly; next still moves on, and previous behaves as usual. A track that fails to resolve skips forward without going round, so a queue where nothing plays stops at its end instead of asking for streams forever. Changing shuffle or repeat drops a preloaded next track that isn't audible yet, and the player asks for the right one.

Play and Shuffle on an artist page set the shuffle setting before they play: Play turns it off and plays the top tracks from the first, and Shuffle turns it on and starts from a loaded track picked at random, with the rest shuffled after it. Both go through the frame's `.Play` with a `Play_Order` (`In_Order` or `Shuffled`), and change the setting only when it differs. Playing a row, from the page or any table, leaves the setting as it is (`Keep`).

Album gain looks at the neighbours in play order, so a shuffled album gets track gain. Both settings are in the settings file. The play order isn't in the queue file: a restored queue with shuffle on starts with the saved track and shuffles the rest. The extras' anchors are, so they come back in their places.

## Resuming after a restart

The queue, its current track and the position in it are kept in `queue.tfq` in the signed-in account's list cache folder, so the next start shows the same track paused where it was. The file is a `Queue_Header` (the current item, the position in samples and the rate it is in, the key of the list the queue came from, and a key new with each write), then a `Queue_Extras` with how many of the rows are extras and an anchor for each (the row it plays after, or -1 for the end), then the queue's rows as a list file (`list_file.odin`), the extras last, read back with the same checks as any cached list. An anchor that isn't an earlier row, or more extras than rows, makes the file damaged. Files of format 1, from before extras, have no `Queue_Extras` and still read. `queue_save` writes it from the disk thread when the queue's rows change. When only its place changes (its current track, pause, a finished seek or the end of the queue), it writes `queue-position.tfq` next to it instead: a `Queue_Position` with the item, the position, its rate and the key of the queue file it goes with, so a pause or a skip doesn't write thousands of rows again. Neither is written as the position moves, and a write still queued is dropped for a newer one. While the list the queue came from is still loading, its pages don't each rewrite the file. It's written when play starts, again each time the loaded rows double, so a crash keeps at least half of them, and once more when the list has loaded or stopped on an error. `playback_shutdown` writes the last position at quit. `app_shutdown` stops the workers and the disk thread before it, so no older write can land after it, and writes any settings still waiting for a worker in between. A header with a negative position, a rate above 768 kHz or a position past a day is damaged; a position without a rate starts the track over. The position file stands in for the header's place only when its key is the queue file's and its place passes the same checks. One left from an older queue file, or a damaged one, is ignored, and the queue reads back at the header's place. Stopping playback, as at sign-out, deletes it, and sign-out deletes the folder anyway. With the fake data there is no list cache, so nothing resumes.

At sign-in the file is read right after the cached sidebar. If nothing plays yet, `playback_restore` rebuilds the queue, starts its track paused at the saved position and resolves its stream at once, so play starts without a wait. If that track's stream fails, the queue moves on to the next track, still paused. The player bar shows the saved position, or a seek made since, while the stream resolves; if the stream's sample rate differs from the saved one, the position is converted. A stream URL that expired by the time play is pressed gets the same single re-resolve as during playback, from the paused position. The restored queue is never re-copied from the open list, even when that list is the one it came from.

## ReplayGain and volume

In bit-perfect mode neither applies (see below). Otherwise ReplayGain follows the ReplayGain setting on the settings page, saved as `replay_gain` in the settings file (`audio.Gain_Setting`). Automatic, the default and what a file without the key or with a name the app doesn't know means, gives a track album gain when it plays as part of its album in order: the queue entry before or after it is from the same album, with the track number one away (`audio.queue_gain_mode`). Otherwise it gets track gain, so a playlist of singles plays at an even level. Track always uses track gain, Album always uses album gain, which keeps the loudness steps between an album's tracks, and Off applies none, for listeners who level-match at the amplifier; the output menu's TIDALfast row then says "Applies volume". A stream without an album gain uses its track gain for Album too. `audio.setting_gain` picks the factor. The factor is `10^(gain/20)`, lowered to `1/peak` if it would push the peak over full scale. The decode thread applies it as it writes frames into the ring, so a change of setting doesn't touch the playing track, whose next 3 seconds are already in the ring at its gain: changing it mid-track would step the level. It applies from the next track. A next track already resolved and waiting for gapless playback gets the new gain through `audio.set_next_gain`, as long as the decode thread hasn't started on it. The volume slider applies after it, in the callback, as the cube of the slider's position, so half way is about -18 dB. A mute sends the player a volume of 0 and keeps the slider's level in the settings to unmute at (see [UI](ui.md#volume)). In bit-perfect mode the slider and the mute button still work and are saved, but play nothing different until the output goes back to the mixer.

## Seeking

A seek shows its position in the player bar at once. It names the track it's for, and the decode thread drops it if that track no longer plays; `play` also drops a seek it hasn't applied yet, so a new track never starts at the old one's seek position. The player bar stops showing the target as soon as its track isn't current, including when the audio moved on to the next track before the seek arrived. The decode thread then looks for the frame to start from. It brackets the target with the SEEKTABLE's points, or with the first frame and the end of the file when there is no SEEKTABLE. It guesses a byte offset in proportion and looks there for a frame header that the next header confirms: sync code, CRC-8, and the next frame starting where this one's samples end. Seekpoints that point before the first frame or past the end of the file are skipped, since a negative offset would read before the stream's window. It narrows the bracket until it has a frame no more than 0.3 s before the target, decodes from there and drops the samples before the target. A guess outside the downloaded window empties it and starts a new range request at that offset, and playback goes on from those bytes. A seek inside the window doesn't touch the network.

Measured from the seek command to the first sample at the new position leaving the callback, against the mock with `-audio-delay=50 -audio-rate=400` (50 ms before each audio response, 400 KB/s per connection, about three times the stream's bitrate) and `TIDALFAST_AUDIO_WINDOW_KB=512`, seven seeks each:

| file | latencies |
|---|---|
| with SEEKTABLE | 25, 62, 101, 109, 113, 142, 278 ms |
| without | 12, 101, 103, 105, 108, 142, 311 ms |

After the callback stopped waking the decode thread, the same setup with SEEKTABLE gave 9, 96, 102, 102, 122, 132 and 300 ms.

The slowest in both is a seek to 18.7 s in a 20 s track, which needed a second probe. With the default window (8 MB then, 3 MB now) the whole mock track is already downloaded, and a seek took 9 ms. Seven seeks into the first album track while it downloads at 400 KB/s, six of them past what had arrived, took 105 to 142 ms with the 3 MB window and 101 to 140 ms with 8 MB, and the one inside the window 10 ms with either. Allowing up to 1 s before the target instead of 0.3 s made seeks that landed far from a seekpoint take 380 to 400 ms, since that second had to download and decode before being thrown away. The player logs each seek's latency to stderr.

## Media keys and Now Playing

Each shell hands the system's media commands to the app as `EVENT_MEDIA` events: `media` is the `Media_Command`, `dx` its value: the position for a seek, the volume slider's position (0 to 1) for `MEDIA_VOLUME`, 1 or 0 for `MEDIA_SHUFFLE` and a `Player_Repeat` for `MEDIA_REPEAT`. Only MPRIS sends the last three. The app handles them in `playback_update`, the same way as the player bar's buttons and slider, and ignores a volume that isn't a number and a repeat out of range. A volume is saved to the settings at once, as when the slider is let go. The shell asks for a frame with each command, so the bar shows the change, and the window goes back to idle after it. The app calls `Shell.set_now_playing` with the title, artist, album, duration, elapsed time, state and the cover as RGBA pixels, which an `Artwork` job fetches at 640x640. It calls it only when one of those changes, since every system moves the elapsed time along by itself while it plays. The shell copies everything before it returns and rebuilds the artwork only when `artwork_key` changes.

**macOS.** `MPRemoteCommandCenter` and `MPNowPlayingInfoCenter` are Obj-C classes, and Odin dev-2026-10 crashes compiling Obj-C method calls, so both live in `shell/shell_cocoa.m`. The shell keeps play and toggle on, since they start the selected row when nothing is loaded. Pause, stop, next and previous are on while a track is loaded, and `changePlaybackPosition` while it has a duration. Stop pauses, as on the other two. With `TIDALFAST_NOW_PLAYING_LOG=1`, each `shell: now playing:` line also lists which commands are on.

**Linux.** `shell/mpris.c` is an MPRIS server, `org.mpris.MediaPlayer2` and its `Player` interface on `/org/mpris/MediaPlayer2`, which GNOME's and KDE's media widgets, their media keys and `playerctl` talk to. The D-Bus side is sd-bus, from libsystemd (or elogind's or basu's copy), opened with `dlopen` after the first frame, so a launch doesn't load it and the app runs without it, only without MPRIS. The build needs only its header (`libsystemd-dev`): the two interfaces are sd-bus vtables, from which it answers `Get`, `GetAll`, `Introspect` and `Peer` itself. Its socket is one more file in the main loop's poll, and connecting, the login and `RequestName` don't wait for the bus. A failed or lost connection is tried again 10 s later, at the next change. The name is `org.mpris.MediaPlayer2.tidalfast`, or `.instance<pid>` after it when another instance has it. Play, Pause, PlayPause, Next and Previous are the app's commands, Stop pauses, and `SetPosition` and `Seek` seek (past the end is the next track, as MPRIS says). `Volume`, `Shuffle` and `LoopStatus` are the player bar's volume slider, shuffle and repeat, and a client can set them; the other properties are read only. The app sends the three through `Shell.set_player_controls` (Linux only; nil on macOS and Windows) at its first frame and whenever they change, from the bar, a key or MPRIS, and the server sends `PropertiesChanged` for those that changed. `Volume` is the slider's position, not the gain, which is its cube, and 0 while the app is muted, so a widget shows silence then and the level again after unmuting. Muting and unmuting change only what the app sends; `set_player_controls` sends `PropertiesChanged` and never a command, so the remembered level isn't written back. A volume written while muted unmutes at it, as the slider does, and 0 written while not muted sets the level to 0. A written volume below 0 is 0 and one above 1 is 1, since the slider stops there, and one that isn't a number is refused with `InvalidArgs`. `LoopStatus` is `None`, `Playlist` (repeat all) or `Track` (repeat one); anything else is refused with `InvalidArgs`. A write takes effect in the server at once, so a read right after it gets the new value, sends its own `PropertiesChanged`, and goes to the app as a `MEDIA_VOLUME`, `MEDIA_SHUFFLE` or `MEDIA_REPEAT` command; the app's answer then matches and sends nothing more. In bit-perfect mode a written volume moves the slider and is saved, as dragging the slider does, and like it changes nothing that plays until bit-perfect output is off. `CanPlay` is always true, since play with nothing loaded starts the selected row. The app's changes go out as `PropertiesChanged`; `Position` isn't one of them, as MPRIS says, so the server works it out when asked from the last elapsed time and the clock, and sends `Seeked` when a new elapsed time is more than a second from that. Clients take the cover as a URL, so it's written as an uncompressed PNG (`shell/png.c`, about 2 ms for 640x640) to `$XDG_RUNTIME_DIR/tidalfast-cover-<pid>-<key>.png`, a new name for each cover so clients don't keep a cached one, and the old file is deleted. The media keys still reach the app directly while the window has the keyboard, for desktops that don't take them.

**Windows.** `shell/smtc_win32.c` sets up the System Media Transport Controls for the window (`ISystemMediaTransportControlsInterop::GetForWindow`) when the first track plays, which loads combase, shcore and shlwapi only then. They show the track, the cover (the same PNG, in a memory stream) and the timeline in the media overlay beside the volume and on the lock screen, and take the media keys while another window has the focus. The WinRT interfaces are declared in the file with their methods in vtable order, from the SDK's `windows.media.h`. The window's thread joins COM's single-threaded apartment then, as a UI thread should; the audio code's COM is on its own threads. Windows calls the button and position handlers on a thread of its own, so they post `WM_SMTC` to the window, and the window procedure sends the command on. With `TIDALFAST_NOW_PLAYING_LOG=1`, a `shell: smtc:` line after each update reads back what the controls hold.

`tests/mpris_linux.odin` asks the server through `dbus-send` on the tests' session bus: the properties, the cover's PNG, each command, the seeks MPRIS says to ignore, and writes to `Volume`, `Shuffle` and `LoopStatus`, with the values it clamps or refuses and the `PropertiesChanged` a `dbus-monitor` sees for the writes and for the app's own changes. `media_sets_the_controls` and `media_controls_follow_the_mute` in `tests/player_test.odin` check the app's side of those commands. The `media` workflow runs the app with the fake data and drives it as the system would: `playerctl` on Linux, including setting the volume, shuffle and loop and reading them back, and on Windows PowerShell through `GlobalSystemMediaTransportControlsSessionManager`, the API the media overlay uses. Now Playing came with platform ABI version 2; text input and accessibility made it version 3 (see [Text input](text-input.md)). Every struct the two sides share has a size check on both sides, and `tests/abi_test.odin` compiles the header and compares each field's offset with the Odin struct's.

## DASH and fMP4

A DASH slot's stream fetches URL 0, the initialization segment, then the media segments in order, each with a plain GET (and a `Range` to resume one the server cut short). Offsets count from 0 at the segment the stream last started from; it can't seek by byte, only start again at a segment (`stream_restart_segment`).

`src/audio/fmp4.odin` parses what's in it. The initialization segment's `moov` box leads to `trak/mdia/minf/stbl/stsd`, whose `fLaC` sample entry holds a `dfLa` box: FLAC's metadata blocks as they'd follow `fLaC` in a file. `parse_mp4_init` returns `"fLaC"` plus those blocks, the last one flagged last, and `mdhd`'s timescale, the track id and `trex`'s defaults. Each media segment is an optional `styp`, a `moof` and an `mdat`. `parse_mp4_moof` reads `tfhd` (track, default sample size, base offset), `tfdt` (the fragment's first sample in the track's timescale) and every `trun`'s sample sizes and data offset, which can carry on from the previous `trun`. A FLAC sample is one FLAC frame.

Data offsets count from the base ISO 14496-12 gives the `traf`: an explicit `base_data_offset` counts from the first byte of the segment file, which the stream records for each segment as it fetches them (`stream_segment_start`); `default-base-is-moof`, or neither flag in the first `traf`, counts from the `moof`. A later `traf` with neither flag would start where the previous `traf`'s data ended, which needs the other tracks' sample sizes, so it's refused with an error that says so.

Segments come from the network, so nothing in a `moof` is trusted. The demuxer reads the header of the `mdat` after each `moof` before parsing it, and every sample must lie inside that `mdat`. A `trun`'s count is checked against its own table and, when the sizes come from defaults, against what's left of the `mdat` (`count * default_size`), all before anything is appended. One fragment holds at most 65,536 samples (a 4 s segment of 192 kHz FLAC has about 190). Box sizes are checked against what holds them, 64-bit sizes above `max(i64)` are refused, and an `mdat` that runs to the end of the segment (size 0) after a `moof` is refused rather than guessed at. A broken box fails the track with the reason in the player bar. `tests/hires_test.odin` checks all of this on hand-made boxes and on 20,000 randomly damaged ones. `tests/corrupt_input_test.odin` feeds this parser, the FLAC header and frame parsers, the MPD, TIDAL's JSON, cover images, the list cache, the queue file and `settings.json` every truncation of a good input, damage at positions from a fixed seed, and hostile size and count fields such as zero, `0xffffffff` and sizes past the end.

The decoder sees the same thing as for a FLAC file: `fLaC` and STREAMINFO (with the sample count zeroed, as for a seek), then frames. The demuxer behind it (`demux_read`) walks the boxes in order, reads each `moof`, then copies its samples out of the `mdat` that follows, and skips any other box. dr_flac decodes 24-bit samples to `v / 2^23` in float, which a 32-bit float holds exactly, so nothing on the way changes a bit.

A seek finds the segment whose start is at or before the target (`dash_segment_index`, a binary search over the timeline's starts converted to samples), starts the stream again at it, decodes from its first frame and drops the frames before the target. The first `moof`'s `tfdt` then says exactly which sample its first frame is, and that, not the MPD's arithmetic, sets how many to drop. A DASH seek always costs one segment request.

## Output

There is no audio library between the player and the system. Each OS has one file, `src/audio/bitperfect_<os>.odin`, with the same procedures, and it plays both ways: through the system's mixer (`mixer_open`), or bit-perfect (`hal_configure`). `hal_start`, `hal_stop` and `hal_close` are the same for both, so falling back from bit-perfect output opens the other kind of stream on the same code.

Through the mixer, the player hands over 32-bit floats at the track's rate with the track's channels, and the system converts them to the device's rate and format and mixes them with the other apps:

- **macOS.** The default output AudioUnit (`kAudioUnitSubType_DefaultOutput`), a C API in AudioToolbox declared by hand like the HAL's. Its render callback fills one interleaved buffer. The unit follows the default output to another device by itself. A mono track is fed to it as stereo, the same on both sides.
- **Linux.** A PipeWire stream without `node.force-rate`, so PipeWire's adapter resamples to the graph's rate (see Output on Linux).
- **Windows.** A WASAPI shared-mode stream with `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM` ([Windows](windows.md)).

The callback there is `mixer_render`: the ring's frames at the volume, ramped over one buffer. Bit-perfect output's is `hal_render`, with a gain of exactly 1.

When the stream loses its device, or the default output moves and the stream can't follow (Windows), the player closes it and opens it again on the default output, from the audible position, as for a lost bit-perfect device below. If no stream opens, the track fails and the player bar says why, such as "no output device" or "PipeWire isn't installed".

`TIDALFAST_AUDIO_NULL=1` and the tests play to the null device instead (`src/audio/null_output.odin`): a thread of the player's that calls `mixer_render` for 10 ms of frames at a time, paced by the clock since it started, so frames leave in real time and nothing reaches a speaker. Stopped, it sleeps on a semaphore.

## Bit-perfect output

Off, the player renders at the track's rate into the default output AudioUnit, and CoreAudio converts to whatever rate the device runs at and mixes with other apps. On, `src/audio/bitperfect_darwin.odin` takes the device itself through the CoreAudio HAL, which is a C API (`AudioObjectGetPropertyData`, `AudioObjectSetPropertyData`, `AudioDeviceCreateIOProcID`, `AudioDeviceStart`), declared by hand in Odin:

1. At the first track, it remembers the device's nominal rate and its output stream's physical format, to restore them.
2. If `kAudioDevicePropertyAvailableNominalSampleRates` has the track's rate, it sets `kAudioDevicePropertyNominalSampleRate`, and a physical format (`kAudioStreamPropertyPhysicalFormat`) at that rate with the track's channels that holds every bit of the track: signed integers of exactly the track's bit depth if the device has them, then the smallest integer depth above it, then 32-bit float, which holds up to 24 bits exactly. A device with only 16-bit formats has nothing for a 24-bit track. It then polls every 2 ms on the decode thread, for at most 2 s, until the device reports the rate, that physical format, and a 32-bit float virtual format at the rate.
3. An IOProc fills the device's buffers from the ring (`hal_fill`). Each buffer is checked: one without data is skipped, frames come from the buffer that holds the fewest so every channel gets the same ones, and whatever is left of a buffer, frames the ring didn't have or bytes past the last whole frame, is zeroed. Mono and stereo go on the device's preferred stereo pair (`kAudioDevicePropertyPreferredChannelsForStereo`, read when the device opens), mono on both, and other device channels are silent. One interleaved buffer that already has the ring's layout is written in place; anything else, such as one buffer per channel, goes through a scratch buffer. It keeps the callback's rules: no locks, allocation, logging or system calls.

ReplayGain and the volume slider are skipped: the decode thread doesn't multiply, and the IOProc copies with a gain of exactly 1. No dither, no conversion. The IOProc sees the virtual format, 32-bit float, and the HAL converts that to the physical format. A float holding `v / 2^23` converts to the 24-bit integer `v` exactly, and the same for 16 bits. If any step above fails (a 192 kHz track on speakers that stop at 96, no format deep enough, a format or rate the device refuses or doesn't report back), the device is put back as it was and the default output unit plays that track, converted, with no ReplayGain. The Output menu then says "Not bit-perfect" and why, such as "no 24-bit format at 96 kHz".

The app doesn't use hog mode (`kAudioDevicePropertyHogMode`). It would keep other apps off the device and change nothing about the track's samples. Other apps keep playing: CoreAudio converts their sound to the device's rate and mixes it in, so the moments they make sound aren't bit-perfect.

The device it uses is the default output when the first track opens it, and it stays that device until the output is restored.

The device gets its rate and format back when bit-perfect output is turned off and when the app quits (`app_shutdown`). The shell turns SIGTERM, SIGINT (Ctrl-C in the terminal) and SIGHUP (the terminal closing) into a normal quit on the main queue, so they reach `app_shutdown` too. Between tracks it isn't restored, only switched.

SIGKILL and a crash can't be caught, and the nominal rate and physical format stay where the last track set them. So while a device is switched, the settings file also holds a `device_change` record: the device's UID, the rate and physical format it had, and the rate the app set. The decode thread publishes it in the player's status and the app saves it as soon as it changes. On a normal quit it goes away. At the next start, if the record is there, the device with that UID still runs at the rate the app set and nobody has changed it since, the app puts the old rate and format back before anything plays, then drops the record. The record is written a frame or so after the switch, so a crash in that window leaves nothing to restore from.

The decode thread also watches the device. Listeners on its `kAudioDevicePropertyDeviceIsAlive` and `kAudioDevicePropertyNominalSampleRate`, its stream's `kAudioStreamPropertyPhysicalFormat` and the system's default output only note what changed and wake the decode thread. CoreAudio may still be running a listener after `AudioObjectRemovePropertyListener` returns, so a listener touches only the player's `Device_Watch`: the flags it sets and the semaphore it posts both live there, and the decode thread sleeps on that semaphore. The watch is never freed. After the player is destroyed nobody waits on it, and a late post does nothing. When the device has gone, as when a USB DAC is unplugged mid-track, the decode thread stops and destroys the dead output without trying to restore anything on it, and plays on from the audible position on whatever is now the default output. If nothing can open, the track fails and the player bar says so. When the default output moves to another device, the device is put back and the track moves to the new default the same way. The default output unit follows the default output by itself.

When another app changes the device's nominal rate or physical format, as a second TIDALfast or Audio MIDI Setup can, the IOProc's frames would play at the wrong speed: CoreAudio converts an AudioUnit's output to the device's rate, but an IOProc writes at whatever rate the device runs. The decode thread compares the device with the rate and format it set, since the listeners also fire for this app's own changes. If they differ, it stops the IOProc, leaves the device as the other app set it and drops the `device_change` record, then plays on from the audible position through the default output unit, which the system mixer resamples. The output button's dot turns to the error colour and its menu says "Not bit-perfect: another app set the device to 96 kHz". Taking the rate back would start a fight between the two apps. The next time the device opens (a track with another format, a lost device or a change of output setting), the player tries bit-perfect output again, so with two instances the device runs at the rate of the one that opened it last.

`tools/audio_top` shows what the devices are doing from outside the app: each output device's nominal rate, buffer size, physical and virtual formats, whether it's running and who hogs it, and on macOS 14 and later every process sending audio and to which device. `-log -interval=2` prints a timestamped line for each change instead, which shows the rate switching per track. It only reads properties.

```
odin build tools/audio_top -out:build/audio_top
./build/audio_top -once
```

Gapless still works at the same rate: the ring doesn't care. A rate change lets the ring play out, stops the IOProc, sets the new rate and starts it again. The player logs the time from the last IOProc call with the old track's frames to the first with the new one's.

### Output on Linux

On Linux, `src/audio/bitperfect_linux.odin` plays through a PipeWire stream, with the same procedures as the macOS file, so the player can't tell them apart. PipeWire is the only output: there is no PulseAudio or ALSA path. libpipewire (`libpipewire-0.3.so.0`, 0.3.50 or newer) is loaded with `dlopen` the first time a track opens the output, so the app runs without it, and the track then fails with "PipeWire isn't installed" in the player bar. The struct layouts, enums and the format pod are written by hand from PipeWire's headers; the pod is byte for byte what `spa_format_audio_raw_build` makes.

With bit-perfect output off, the stream offers 32-bit float at the track's rate with the track's channels, at the positions FLAC gives them, and sets neither `node.rate` nor `node.force-rate`. PipeWire resamples it to the graph's rate, mixes it to the sink's channels and applies the stream's volume, which the session manager may restore. `mixer_open` waits up to 2 s for the stream to be linked (paused or streaming) and fails the track otherwise. A stream that fails or loses its sink later is opened again.

With it on:

1. The stream offers one format: 32-bit float, stereo, at the track's rate. Mono goes out on both channels; more than two channels is refused.
2. Its properties ask for the track's rate (`node.rate = 1/<rate>`) and force the graph to it while the stream is active (`node.force-rate = 0`, which means "the rate in node.rate"), the way the macOS code sets the device's nominal rate. `state.restore-props = false` keeps the session manager from restoring a stream volume saved for the app.
3. The stream connects to the default sink with `AUTOCONNECT | MAP_BUFFERS | RT_PROCESS`, and `hal_configure` waits up to 2 s until the graph's rate (`pw_time.rate` in the process callback) is the track's. Until then the callback sends silence and leaves the ring alone. If the graph doesn't get there, the Output menu says why, such as "PipeWire stayed at 48 kHz", and the track plays through a stream that doesn't force the rate.
4. The process callback fills PipeWire's buffer from the ring through `hal_fill`, under the same rules as the IOProc. With the graph at the stream's rate, PipeWire doesn't resample, and its conversion from `v / 2^23` floats to the sink's integer format is exact.

`resample.disable` isn't set. It would only matter when the rates differ, and then the app plays nothing; with it set the stream might not link while the graph still runs at the old rate.

Paused, the stream is set inactive, so an idle app uses no CPU. After PipeWire's suspend timeout the graph goes back to its default rate, and starting again forces the track's rate again. If the graph stays off the track's rate for 2 s while playing (another app forced its own rate, or PipeWire moved the stream to a sink that runs elsewhere), or the stream fails or loses its sink, the output counts as lost: the player closes it and opens it again from the audible position, as when a Mac's DAC is unplugged. PipeWire follows the default sink by itself.

There's nothing to restore: the graph's rate goes back when the stream is gone, so there's no `device_change` record. Other streams, such as notifications, are resampled to the graph's rate and mixed in while they play, so those moments aren't bit-perfect, the same as on a Mac.

What the app can't see from its stream: a sink whose hardware can't run at the forced rate resamples inside PipeWire, and a software volume on the sink below 100% scales the samples. Check with `pw-top`, which shows each node's rate and format.

## Output settings

The player bar has an output button, left of the volume: a speaker and the name of the device the sound goes to ("Output" before anything has played), borderless like the bar's other controls. The speaker's colour is the path: cyan when the device gets the track's samples unchanged, the error colour when bit-perfect output is on and the system mixer plays instead, because the device can't take the format or another app changed its rate, and grey with bit-perfect output off, since then the conversion is the user's choice. The track's own format, such as "FLAC, 24-bit, 96 kHz", goes on a third line under the title and artist, so the button speaks only for the output (`src/app/output.odin`). Clicking that line opens the same menu as the button.

The button opens the signal path: a row per step from the track to the device (Track, TIDALfast, CoreAudio or PipeWire, the device), each with a dot in the same colours and what it does to the samples, such as "No volume or ReplayGain" or "Resampled to 48 kHz and mixed". Under them is a line saying what reaches the device, with the reason when it isn't bit-perfect, then the "Bit-perfect output" switch. The rows come from the player's `Device_Info`, which has the device's name, nominal rate and physical format on both paths. While the system mixer plays, the player listens to the default output's rate and format too, on macOS, and updates them, so the rows stay true when another app changes the device. The app keeps the last open output's info while the device reopens between tracks, so the button doesn't flicker. A change goes to the player at once: it closes the device (restoring it) and plays on from the audible position through the new output, since the ring's frames went through the old one's gain. The settings go in `~/Library/Application Support/tidalfast/settings.json` (`{"bit_perfect": true, "scrollbars": "Floating"}`, plus `device_change` while a device is switched, see above) and are read when the app starts. A `hog` key from older files is ignored. A choice written as a number out of its range (`"repeat": 7`, `"replay_gain": 9`) reads as the default, since the player bar indexes tables by it and the settings page would show no choice selected, and a `device_change` without positive rates is ignored.

## Scrollbars

Every `ui.scroll_view` draws a 6 pt scrollbar over its right edge while its content is taller than it. The settings page (see [UI](ui.md#the-settings-page)) has three modes, saved as `scrollbars` in the settings file. Floating, the default, fades in when the view moves and out a second after it stops, unless the mouse is on it; it asks for one wake-up to hide and draws nothing in between. Docked always shows and takes a 10 pt gutter from the rows. Never draws none. The thumb is built from the last layout's content height, then placed again for this frame's once it's laid out (`thumb_fit`), so a row that comes or goes moves it in the same frame. Pressing the thumb drags it; pressing beside it centres the thumb there. The drag is applied when the view is built, before its rows, so the virtual rows match the new offset.

Under the scrollbar modes the page has the player bar's, saved as `bar`, only where the renderer has backdrops. Blurred, the default, floats the bar over the views' bottoms and blurs them (see [UI](ui.md#the-window-on-macos)). Solid puts it back under the views, with nothing drawn under it.

Saving goes through `settings_queue`: it puts the settings in Data's `Settings_Store` as the newest, with a generation number, and has a worker flush them. A flush holds the store's write mutex for the whole write, reads the newest settings when it starts, and skips the write if the file already has that generation. So with four workers there's still one write at a time, older settings never land after newer ones, and a burst of clicks makes few writes. Each write goes to a temp file of its own name, which is synced and renamed over the file. The path is the store's own copy, freed only after the workers have stopped.

It also checks that a new list's row doesn't take the old list's preloaded track, that the toggle starts playback from idle and after the end, and that a seek still pending when the track changes or the app reloads doesn't pin the player bar. Those four feed made-up player statuses to `playback_observe`, the half of `playback_update` that reads the status, so they run without waiting on the audio. The Play next and Add to queue tests there check the order tracks play in: one insert and two, at the end, with nothing queued, after the queue played out, with shuffle and repeat all, shuffle turned on and off after an insert, an insert while the next track is preloaded or already audible, and the album gain an extra gets. `tests/list_cache_test.odin` checks that extras keep their places as a list's pages arrive and its rows move, that they're saved and restored, and the queue file's anchors, damaged ones and format 1. `tests/audio_test.odin` checks on the null device that `play` drops a pending seek, that `status` never pairs a mark with another mark's position, that the callback never posts the decode thread's semaphore or leaves a wake pending, and that a listener still running after its player is destroyed touches nothing the player owned. On a test mock it checks that a read longer than the window, and reads through a window smaller than the history kept behind, both complete (`stream_reads_past_its_window`); that a window filling up leaves one wake-up pending, not one per chunk (`stream_wakes_coalesce`); that a paused track waiting on a server that never answers doesn't wake until a command posts (`paused_read_does_not_poll`); that clearing a stream releases its window, which only the Linux run can see, since there the released pages read as zeros (`stream_clear_releases_the_window`); and that a track with 4 MB of cover art plays while the slots keep only a few header bytes, and one with a 20 MB ID3v2 tag fails (`flac_header_size`). `flac_header` checks that a file cut inside its last metadata block needs more bytes.

## CPU

Apple M1, the mock album playing to the null device: 1.5% with an optimized build and about 4% with a debug one, mostly the four UI frames a second for the progress bar. Paused, the device is stopped and the decode thread sleeps on its semaphore: 0.0%.

Measured again after the callback stopped waking the decode thread, with CPU time from `ps`: the fake tones with an optimized build use 0.20 s in 15 s of playing (1.3%), and nothing in 7 s idle before playing or 20 s paused. The mock album with a debug build uses 2.3 to 3.6%, and nothing in 20 s paused once the next track's download has filled its window.
