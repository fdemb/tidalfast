# UI

`src/ui` is an immediate-mode UI after Ryan Fleury's box UI in raddebugger. Each frame the app builds a tree of boxes. `end_frame` lays it out, draws it with `render` and `text`, and records where every box landed. The next frame tests input against those rects, so a click goes to what was on screen.

```odin
ui.begin_frame(&s.ui, events, r, &s.text, w, h, time, input.mouse_buttons)
{
	ui.row("body", {}, ui.fill(), ui.fill())          // parent until the end of the scope
	ui.label("Your Library", ui.text_size(), ui.px(52))
	if ui.button("Play##play").clicked { play() }
}
animating := ui.end_frame()                             // goes to the shell as Frame_Result.animating
```

## Boxes and keys

A box built with an ID string is keyed by an FNV-1a hash of the string, seeded with the key of its nearest keyed ancestor, so `"##row12"` in two lists gives two keys. `"Play##row12"` shows "Play" and hashes the whole string. `"Pause###play"` hashes only `"###play"`, so a label can change without the box losing its state. Keyed boxes come from a pool of 8,192 in the persistent arena, found through a 4,096-bucket chained hash table, with a free list. Each one keeps its rect, clipped rect, content size, scroll offset and animation values. `begin_frame` frees every box that wasn't built in the previous frame, going through the part of the pool in use rather than the 4,096 buckets. A box with no ID (`ui.label`, spacers) lives in the frame arena for one frame and has no state. They're taken 64 at a time, which saves an allocation per box. A key built twice in one frame makes the second box keyless instead. When the pool is full, new keyed boxes come from the frame arena with key 0 and keep no state. The UI logs that when it starts, at most once a second, and the overlay's last line turns red with the number of boxes that missed out.

`State` and every box are plain data: pointers into the persistent arena and the frame arena. The only procedure pointers are the shell's clipboard, which `set_clipboard` sets every frame. The renderer and text pointers and the tree are set again by `begin_frame`, and the package keeps its current `State` in a thread-local pointer that `begin_frame` sets. Strings given to boxes must live until `end_frame`. That holds for literals, the persistent arena and the frame arena. The views build their per-frame ids and labels with `cat` and `num` in `library.odin`, which join strings and write numbers into the frame arena, since `fmt.tprintf` costs three to five times as much and a frame builds over a hundred of them. An icon button's or a link's text is set as its label apart from the id it's keyed by, so neither is joined into a `"label###id"` string every frame.

## Sizes and layout

Each box has a size per axis: `px(n)`, `text_size(pad)` (the label's width or line height plus `pad`), `pct(f)` of the nearest ancestor with a size of its own, or `children_sum()`. `fill()` is `pct(1, 0)`. Each size has a strictness: how much of it the box keeps when its parent has too little room. `layout.odin` solves Fleury's five passes per axis: standalone sizes (pixels, text), upwards-dependent (percentages, skipping ancestors sized by their children), downwards-dependent (children sums), violations, then positions. It does all ten in two walks over the tree, since the axes don't depend on each other and each pass reads only what the earlier ones wrote for the box, its ancestors or its children: one does the first two passes on the way down and the third on the way up, shaping the labels of text-sized boxes as it reaches them, and the other fits a box's children into it and places them before going into them. The violations pass runs from the root down, and before it solves a box's children it takes their percentages again from the box's final size. Without that, a `fill()` inside a `fill()` that its parent shrank kept the outer one's first size, and a strict `pct(f, 1)` inside it, like the progress bar's fill, came out as a share of the whole window. When the children along a box's child axis don't fit, each gives up `size * (1 - strictness)` in proportion until the overflow is gone. A box with `Shrink_From_End` takes the room from its last children instead: the first ones stay whole, the one that crosses the edge is cut short, and the rest get none. Across the axis a child larger than its parent is cut to fit. Scroll views allow overflow on their scroll axis and skip that step. A box's `gutter` comes off its width before its children get any; a docked scrollbar uses it. A box with `Floating_X`/`Floating_Y` sits at `fixed_pos` outside the flow. So a row of `px(44)`, `fill()` and `px(56)` gives the middle box whatever is left. A box with `Center_Children` starts its children half the room they leave along its child axis, where two `fill()` spacers around them would put them, without the two boxes; covers and icon buttons are centred in their cells this way.

## Styles

A box takes its look from style stacks, after raddebugger's (`src/ui/stacks.odin`): its font, font size, text colour, alignment and padding, background, border, hover and press colours, corner radius, and flags added to the ones it's built with. `box_make` reads the top of the stack. A scope pushes a copy of the top with one value changed until the end of the enclosing block, and `set_next_*` sets a value for the next box built only, whatever the stack holds.

```odin
{
	ui.text_style(.Regular, 13, SECONDARY)
	ui.radius(6)
	ui.set_next_background(SURFACE)
	ui.row("##row", {.Draw_Background})
	ui.label("Artist")
}
```

Use them this way:

- A style that several boxes in a subtree share goes in one scope, as the transport buttons' `radius(18)` and the track row's `radius(6)` do.
- `set_next_*` goes right before a box that the next call builds first: `box_make`, `label`, `row`, `column`, `button`, `text_field`. A helper that builds a column around its box, or may build nothing, takes its look as parameters instead, as `icon_button` and `cell` do. A `set_next` there would land on the wrong box, or on none. Open or close no scope, `floating()` or `menu()` between a `set_next` and its box.
- A box's own style field is written after it's built only when the value comes from that box's state, such as `hot_t`, or right under an `if` that tests the box, such as a drop hovering it. `test_app_styles_go_through_the_stacks` fails on any other write.
- Widgets whose look belongs to the UI (menus, menu items, tooltips, scrollbars) set it with `set_next_*`. `floating()` and `menu()` start from the default style, so a menu or a tooltip looks the same wherever the code builds it. A `button`, a `link` and a `text_field` take theirs from the stacks; a text field's border is the accent while it has the focus.

Opacity, positions and sizes aren't stacks. Opacity already multiplies everything inside a box, so a stacked value would multiply again at every level, and sizes are `box_make`'s arguments. `begin_frame` empties the stacks. A frame that leaves a scope open or a `set_next` unused, or opens or closes a scope between a `set_next` and its box, logs an error once, which fails any test that draws it.

## Input

`process_events` folds the frame's events into `Input` and walks them in order. The hit list from the last layout holds every keyed box that is clickable, focusable or scrolls, with its clipped rect, in drawing order. The hot box is the last clickable one under the mouse, so children beat parents and the floating layer beats everything. A press makes the hot box active for that button and clicks it. A box with `Click_On_Release` clicks on a release over it instead, so a drag can start from it without the click firing. The links in the track table have it, since a drag from them drags the row. While the left button is held only the active box can be hot. `ui.signal(box)` reports hovering, held, pressed, released, clicked, double-clicked (from the shell's click count), right-clicked (on mouse down, as macOS menus do, control-click included), dragging (past 4 pt, until the release) with the drag delta, and scroll. `Signal.mouse` is the current mouse while held and where the button came up when released, and the drag delta runs to the release too. A press and release in one frame, which happens when the events arrive between two frames, still reports both, so sliders and handles act on `held || released` with `Signal.mouse` rather than on `held` alone. `Input` keeps where each button last went down and came up.

A release can go missing, as when the mouse comes up in another app after the window lost focus. So the app passes `Frame_Input.mouse_buttons` to `begin_frame`. The shell fills it every frame with the buttons down in the whole session, which on macOS it asks CoreGraphics for (`CGEventSourceButtonState`). A button held since an earlier frame that is up in hardware, with no event for it this frame, gets one more frame for its release to arrive, and then the UI lets go of it: no release, no click from a release, and a drag it held ends without a drop. Without the hardware state, as in the tests, the UI goes by the events alone.

A clickable box also counts as hovering while its clickable child is hot, so a row stays lit under its own "more" button.

Keyboard: Tab and Shift-Tab move the focus through focusable boxes in drawing order, starting at the first or last when nothing has it. The arrows move it to the nearest focusable box with the same keyed parent in their direction: past the focused box along the arrow's axis and overlapping it across. So Up and Down move along a column, Left and Right along a row of cards, and all four through a grid of them. With no box overlapping it that way, an arrow goes to the nearest box that way at all, so a box off to the side is still reached. Left from Back reaches Home in the sidebar, and Down into a grid's short last row reaches its last card. A box with nothing that way, or a text field with the focus, leaves the key to the field or to `ui.take_key`. A list that moves a selection with the arrows needs a keyed parent of its own, as the artist page's top tracks have, so no other box in its group takes the keys first. Enter clicks the focused box (`Signal.keyboard` says it came from a key). Space clicks only in an open menu. Anywhere else it waits for `ui.take_key`, so the library can play and pause with it whatever has the focus. Escape cancels a drag, or else closes the menu, or else drops the focus. When the keyboard moves the focus, the scroll views around the focused box scroll the least it takes to show it, along each axis the nearest one that scrolls that way. So a card in a sideways row inside a page that scrolls down comes into view across and down. A box larger than the view, like the track table, doesn't scroll while any of it shows, so Tab into the table keeps the reader's place; out of view, its nearer end comes in. A press moves the focus to the box clicked, or its nearest focusable ancestor. Keys the UI doesn't use wait in a list for `ui.take_key(code, modifiers)`. With `repeats = false` it skips the presses the OS repeats while a key is held. A text field's keys go into the list as well, so a shortcut that works anywhere checks `ui.text_focused()` first. Focus from the keyboard draws a ring; focus from a click doesn't. A box with `No_Focus_Ring` shows its focus another way: menu items with their highlight, and the track tables with their selected row.

## Scrolling

Each axis scrolls on its own. A scroll goes, along each axis, to the innermost scroll view under the mouse that allows overflow that way. So a row that scrolls sideways inside a page that scrolls down takes the sideways part of a diagonal trackpad scroll, and the page takes the rest. A wheel with no sideways delta over the row scrolls the page. A trackpad gesture keeps both of its views until the next gesture, momentum included. A mouse wheel scrolls whatever is under the mouse. Trackpad deltas move the view straight away. macOS sends the momentum phase as more deltas, and the Linux shell sends its own the same way ([Linux](linux.md#touchpad-scrolling)), so the UI adds no inertia of its own. Wheel lines (16 pt each) move a target that the view eases toward. Both are clamped to the content size from the last layout while building, then again to the layout just done, since the content may have shrunk. `ui.virtual_rows(view, count, row_h)` builds only the rows in view, `floor(offset / row_h)` to `ceil((offset + height) / row_h)`, plus one row past each edge so the keyboard can move onto it, with a spacer above and below for the rest. It goes by the view's size in points (`ui.build_size`), so the app gives every scroll view its size. `draw_library` works the sizes out from the window's, as RAD Debugger does for its panels: the body is the window less the player bar and the status bar, the sidebar's playlists are the body less what's above them, and the main view is the body less the room for Back and Forward and the login notice, then less the results' header and the tabs on the search page. The boxes above take their heights from the same constants. A view sized this way builds the rows that fill it in its first frame and in the frame after a resize. A view sized with `fill()` goes by the last layout instead, so its first frame builds no rows. `views_reach_the_bottom_of_the_body` checks that each view ends at the bottom of the body on every page. Its `start` is where row 0 sits in the content, for rows under a header that scrolls with them; the rows can then go in a box of their own inside the view. A row that isn't built has no box, so a focused row scrolled out of view loses the focus. The sidebar's playlists are built this way, and a focused playlist scrolled away by the wheel or the trackpad is no longer focused when it comes back.

A trackpad scroll past either end of a view stretches it (see `src/ui/stretch.odin`). The view's offset stays inside the content, and layout draws the content further along by the stretch (`drawn_off`), so code that reads `view_off` never sees it go past the end. While the fingers are down, the stretch is a twentieth of the scroll past the end, after the first 10 px, which a stray move doesn't reach. Scrolling back takes the stretch in point for point before the view moves. When the fingers lift, or momentum runs into the end, the stretch goes back as `(s + 0.31 v t) e^(-12.5 t)`, where `s` is the stretch and `v` the speed of the last event toward the end, so a fling carries the content past where it hit before it comes back. Fingers back on the trackpad stop the bounce where it is. Momentum that was already running when a bounce began can't stretch the view again after it settles; only momentum that begins later can. Mouse wheels never stretch a view, and nor do Windows touchpads, whose scrolls carry no phases.

## Animation and redraws

`hot_fade`, `active_t` and `focus_t` move at a constant speed, up by `dt / FADE_IN` and down by `dt / FADE_OUT`. `hot_t` is `hot_fade` along a smoothstep curve, and it's what draws a hover. A box with `Instant_Hover`, such as a list row or a card, goes to 1 and back to 0 with no fade, so every row a fast mouse crosses reaches the same brightness, however few frames it was hot for. The hot box comes from the last frame's rects, so a row that scrolls under a still mouse would be hot a frame late, and lit in the wrong place. Having no fade to keep, an Instant_Hover box is lit again in `end_frame`, after layout and before drawing: the one under the mouse in this frame's rects lights, and the one the build lit goes dark if it's no longer there. What the app shows with a row, like a track row's heart and "more" buttons, follows it with `ui.show_on_hover(b, row)`: `b` is drawn at least as opaque as the row's `hot_t`, read when it's drawn rather than while it's built. A fade that reverses partway starts from the value it reached, so it takes only as long as the distance back. `open_t` and the scroll offset ease toward their targets with `v += (target - v) * (1 - exp(-dt * k))`. When the last frame was still animating, `dt` is the time since it, capped at 1/30 s. After a frame that settled, nothing was easing across the gap, so `dt` is one refresh of the display: `Frame_Input.frame_interval`, which the app passes to `ui.begin_frame`, or 1/60 s when the shell reports 0 for unknown. The interval after that may be irregular, since the swap chain may still be settling, so that frame steps no more than one refresh either. The macOS shell reports its display link's interval, the Wayland shell the time between frame callbacks asked for in the callback before (0 until there's been one), and the Win32 shell the refresh rate of the monitor the window is on. A value within its epsilon snaps to the target. Anything still moving sets `animating`, which `end_frame` returns and the app passes to the shell. A new keyed box asks for one more frame, since it has no rect to test input against yet, and so does a hot box that changed under a still mouse. So does a scroll view whose layout didn't match what its children were built for: its offset had to be clamped (the content shrank), or, for a view sized with `fill()`, its size changed. The next frame builds it right. At most 3 such frames come in a row, so a layout that never settles can't keep the window drawing. The count starts over in a frame with events or a new window size, and when the app calls `ui.data_changed()`, so the limit only stops retries with nothing new coming in. Tooltips keep frames coming during their half-second delay. Once everything settles, no more frames are asked for and the window goes back to 0% CPU.

## Floating layer

`ui.floating()` makes a second root the parent until the end of the scope. It is laid out after the main tree, drawn after it with no clip from it, and its boxes come last in the hit list, so they get input first. Menus, tooltips and the drag ghost live there. `ui.open_menu(id, pos)` opens a context menu, or with `up` one whose bottom is at `pos`, for a button at the bottom of the window, and `if ui.menu(id) { ui.menu_item(...) }` builds it while it's open or fading out. The deferred end of `ui.menu` runs at the end of the `if`, so the items must go inside its block. The focus is the menu's highlight, as in a macOS menu: an item looks the same hovered or focused and has no focus ring (`Focus_Is_Hot`). Opening the menu from the keyboard highlights its first item. Opening it with the mouse highlights nothing until the mouse moves over an item or an arrow key picks the first or last. Moving the mouse highlights the item under it, or nothing when it's over no item, and the arrows move the highlight from there even with the mouse still over another item. While it's open, Tab and the arrows move only among its items and Enter and Space click only them, and closing it puts the focus back where it was. The item highlighted when it closed stays lit while it fades out (`menu_lit`). A left click outside the menu closes it and goes no further; a right click closes it and goes on, so it can open another. A menu fading out takes no input, and neither does one that closed while it was being built, as when an item was clicked: its boxes stay out of the hit list. `fit_floating` places menus and tooltips after layout, when their size is known, moves them into the window and flips them above when there's no room below. Placing them while they're built would go by last frame's size, which a new box doesn't have. `ui.tooltip(signal, text, shortcut)` shows text in a box centred under the box, or above it when there's no room below, once the box has been hovered for 1 s. A shortcut, such as the player bar's `⌘→`, goes in a keycap at its end. `fit_floating` places it from the box's rect in this frame's layout (`anchor`), so it doesn't move with the mouse, and every button in a row puts its tooltip on the same side. Within 1 s of the last tooltip, the next one shows at once without fading in, so moving the mouse along a row of buttons shows each one's. A button that scrolls under a still mouse waits for the delay, so a scrolling list doesn't flash tooltips. A click hides the tooltip until the mouse leaves the button, so it doesn't come back over what the click did, such as a menu or Play turning into Pause.

## Drag and drop

A source calls `ui.drag_begin(payload)` once its signal says dragging. From then on the UI owns the drag: any left release ends it, wherever the mouse is and whether or not the source box is still built, and Escape cancels it. Moving on with the button still held after Escape doesn't start a new one. `ui.drag_payload()` reports the drag while it goes on, for drawing a ghost. A target calls `ui.drop_hover(box)` to light up and `ui.dropped(box)`, which returns the payload in the frame a drag ends over the box. A drag that goes down, past 4 pt and up between two frames still drops: its source's signal says dragging and released, `drag_begin` takes it, and since targets built before the source have already asked, `dropped` returns it in the next frame, tested against the rects it was released over. The release asks for that frame.

## Drawing

Box flags pick what's drawn, in this order: shadow, background (optionally a vertical gradient), the hover and press overlays faded by `hot_t` and `active_t`, border, focus ring, label, then the children inside the box's clip if it has `Clip`. `opacity` multiplies the box and everything in it. A label is centred vertically, aligned left, centre or right inside `text_pad`, and truncated with an ellipsis to the box's width. A box whose clipped rect is empty draws nothing itself. Labels are shaped when drawn, through the text cache, unless the box is sized by its text, in which case layout shapes it first. Nothing in the UI allocates outside the frame arena after `ui.init`.

## The library screen

`src/app/library.odin` follows spotifast's layout, in neutral greys with a cyan (#00ffff) accent: a sidebar of 32 fake playlists, 250 pt wide by default, resized with a 5 pt handle between 210 and 600 pt (it stops growing once the main view would go below 360 pt). Its playlists are 48 pt rows 2 pt apart, a 36 pt cover next to the name and the number of songs. The open playlist, and Home or Search while their page shows, sits on a lighter grey with a hairline border and a 1 pt shadow; the playlist the play queue came from has its name in the accent, and four still level bars while it plays (`sidebar_queued`). A click opens a playlist, and a double-click also plays it from the top, keeping shuffle as it is; when its songs haven't come yet it plays once the first one has, unless another list opens first (`play_when_ready`). Next to it is the main view with the list's header and the 10,000-row track table (see [The list header](#the-list-header)), and the 88 pt player bar runs along the bottom. At the bottom of the sidebar, above the player bar, is the user row (`src/app/user_menu.odin`). It shows the signed-in user's picture in a 24 pt circle, or the first letter of their name until the picture comes. Hovering or focusing the row fades in a full-width button with the name and an up and down caret. A click opens a menu above it with Settings, which shows the settings page, and Log out, which calls `sign_out` with no note. The name and picture come from TIDAL's `users/{id}` once per login. With the fake data the row says Fake data and its menu has no Log out. Back and Forward are a pill floating over the main view's top left corner, ‹ and › with a line between them, 8 pt in from the top and the side. They go through the last 50 places visited (`History` in `library.odin`): sidebar playlists, albums, artist pages, an artist's full top tracks and shelf grids, playlists from search, and searches. A TIDAL playlist is found again by its id, so Back still opens it after the sidebar changes order, and opens Liked Songs once it's gone. A search typed a letter at a time is one place, so Back from a list opened in the results shows the results for the final query, with the query back in the field. Rows are 56 pt. The columns follow spotifast's `columns`, measured on the main view's width, and the list's kind (`List_Kind`) picks them in `track_columns`: # and title always, and the cover always but on an album, whose rows are all the same album. Album shows above 560 pt (28% of the width, 140 to 360 pt), again not on an album, and date added above 760 in playlists and Liked Songs. Albums, artists and search results have no date added, so they never show it. Duration and the "more" button always show. Between date added and duration is the heart column: a filled heart in the accent when the track is liked, an outline otherwise, shown when the row is hovered or selected like the "more" button. A click turns the heart at once (see [TIDAL data](tidal-data.md)) and selects the row. Hovering lights a row; a click selects it; a double-click plays it (see [Playback](playback.md)), and the row playing is lit. The queue remembers which list it came from (its kind and TIDAL id, or the search query), so the row stays lit after going to another list and back, and the same track in another list isn't lit. When the reopened list's rows differ, the first row with the playing track's id is lit. A row's artists and album are links: clicking one opens that artist's page or that album, the same places as Go to artist and Go to album. Each of a song's artists is its own link, with the commas between them as plain text. A row keeps every artist's id and where its name sits in the joined artist string (`Artist_Ref`), so a name with a comma in it, like "Tyler, The Creator", stays one link. A link is only as wide as its text and is underlined while the mouse is over it (`ui.link`). When the artists don't fit, the one that crosses the edge ends in an ellipsis and the rest get no room. The layout decides this (`Shrink_From_End`), so it holds from a row's first frame and right after a resize. Pressing, right-clicking or dragging on a link does the same as on the rest of the row. In the player bar, the title opens the playing track's album and each artist opens that artist. A heart right after the title likes or unlikes the playing track. Rows without an album or artist id show plain text. A right click or the "more" button opens a context menu with Play, Go to album, Go to artist and Copy song link (see [Search](search.md)). Dragging a row onto a playlist shows a ghost and a drop highlight, and dropping it adds the track on TIDAL, or likes it on Liked Songs (see [TIDAL data](tidal-data.md#the-list-cache)). The drag goes through `ui.drag_begin` with the row index, so releasing after the row has scrolled out of view still ends it. With the table focused, the arrow keys, Page Up/Down and Home/End move the selection and scroll it into view, and Enter plays it. The table draws no focus ring, since the selected row shows where the keyboard is. When the keyboard focuses it with nothing selected, the first row in view is selected. The player bar has shuffle, previous, play/pause, next and repeat, with Phosphor icons (see [Text](text.md)). Play/pause is a 44 pt disc of glass with a white icon, which bends the bar's blur at its rim ([Renderer](renderer.md#glass)). Shuffle and repeat light in the accent colour with a dot under them while on, and repeat shows a 1 on repeat one. There's a progress bar that seeks on click or drag and shows the drag position while held, elapsed and remaining time, and the volume slider. The times and the table's Time column are as wide as the widest value their pattern can show, measured with the font's widest digit, so they're never cut off; the progress bar and the volume slider take what's left. Rows whose page hasn't arrived yet show their number and grey bars. With `TIDALFAST_FAKE=1` the 32 playlists and 10,000 rows are the fake data again and covers are gradients.

### Shortcuts

`library_shortcuts` runs at the end of `draw_library`, so a view that takes a key first keeps it, as the track table does with the arrows. Space plays and pauses, Cmd-Right and Cmd-Left go to the next and previous track, and Cmd-Up and Cmd-Down change the volume by 10%. They are Ctrl on Linux and Windows. A held Space doesn't repeat. None of them work while a text field has the focus, and the login screen has none. The Back and Forward buttons on a mouse do what Back and Forward in the main view do, with a text field focused too. The UI doesn't press, focus or drag anything with those two buttons; it keeps their presses for `ui.take_button`, and with a menu open they only close it.

### The status bar

`TIDALFAST_STATUS_BAR=1` adds a 22 pt line under the player bar, for agents that check the app through captures and the accessibility tree. It says whether a track is playing, paused or ended, its title and artist, and then the status (`status_text`: a copied link, an add to a playlist, a list's error, TIDAL's rate limit), as "Playing Song by Someone · Added Song to A playlist", or "Nothing playing". It's a static text in the accessibility tree. The views show neither anywhere else, except errors, which also get a toast.

### The error toast

An error shows in a toast centred over the bottom of the views, 16 pt above the player bar (`src/app/toast.odin`): TIDAL's rate limit with its countdown, a list that failed to load, a failed search, a failed add to a playlist, and `Data.message` (the sidebar, following, the settings, the Keychain). `current_error` picks the most pressing one, and the status bar's text comes from it too. A toast stays 6 s (`TOAST_SECONDS`), longer while the mouse is on it, and a click dismisses it. An error counts as new when its source or text changes, except the rate limit, whose countdown changes every second. The toast asks for a frame at the time it should hide with `ui.wake_at`, and once a second during a rate limit, so it keeps no frames coming while it waits. Playback errors stay in the player bar under the title. Copied links and successful adds show only in the status bar. Without the variable the bar isn't built.

### The window on macOS

The window has no titlebar of its own: the shell hides the title, makes the titlebar transparent and puts the view under it, so only the close, minimise and zoom buttons stay. On Windows the app draws those buttons itself, at the top right (see `docs/windows.md`, The window's top), and on Linux it does unless the compositor draws the title bar (on a tiling compositor, or with "System" in the settings), round and where GNOME's button layout puts them (see `docs/linux.md`, The title bar). Each frame it passes the titlebar's height and where the zoom button ends (`Frame_Input.titlebar_height` and `titlebar_inset`, both 0 in full screen, and on Linux with the compositor's title bar). On macOS, and on Linux with buttons on the left, the sidebar keeps room above Home as tall as the main view's room for Back and Forward (`nav_h`), under the window's buttons; elsewhere Home starts `SIDEBAR_PAD` from the top (`sidebar_top`). The login screen starts with an empty strip of the same height. The main view keeps `NAV_H` (50 pt) at its top for Back and Forward. Home, the artist page, a track list and the search results keep that room at the top of their scroll view (`nav_reserve`), so at the top nothing is under the pill, and scrolled down they run under it while it floats over them. The pill is built after the view, so it is drawn over it and takes the clicks there. The empty search page, an artist's grids and a view under the login notice keep their headers still, and the main view keeps the room above them instead. The room moves the window, as a toolbar does. Boxes flagged `Window_Drag` (that strip and the room at the top of the sidebar) go to the shell through `Shell.set_drag_regions`, less what's drawn over them that takes clicks: `end_frame` walks the clickable boxes drawn after each drag rect from the top down (`cut_drag_regions`), and the topmost one at each point decides. A button, a link or a scrollbar under the strip is cut out, so it takes its press. A box flagged `Click_Shield`, clickable only to stop presses reaching what's under it, such as the list's pinned bar and the player bar, keeps its part of the region, and the rows hidden under it don't count. A press there moves the window, and a double-click zooms or minimises it as System Settings says (on Linux, maximises or restores it, and a right click opens the window manager's menu). `Metal_View` returns NO from `mouseDownCanMoveWindow`, so a press anywhere else in the strip reaches the app.

The sidebar, the main view and the player bar are opaque. An earlier version had an `NSVisualEffectView` behind the window, showing the blurred desktop through a translucent sidebar or player bar, and dropped it: next to the player bar's own blur of the views it looked worse, and the window has to be composited with alpha for it.

Where the renderer has backdrops (`render.BACKDROPS`, Metal and Vulkan), the player bar floats over the bottom of the window, and the sidebar, the track list, the search results, the grids and the artist page run under it (`bar_inset`, a scroll view's `inset_end`, so their ends still scroll clear of it and the scrollbar stops above it). Its background is a `Draw_Backdrop` box: a blur of the views under it reaching `BAR_BLUR` (20 pt), its colours saturated by `BAR_SATURATION` (1.8), under `BAR_TINT`, the panel grey at 75%, like a macOS material (see [Renderer](renderer.md#backdrops)). The bar is clickable, so a press on its empty parts doesn't reach the row under it. With the Solid player bar in Settings (`Settings.bar`), the bar sits under the views.

`TIDALFAST_BLUR_REFERENCE=<material>[,<height>]` shows AppKit's blur to compare with. The app leaves the bar out, the views still running under where it goes. The shell covers the bottom `<height>` points (88 by default) with an `NSVisualEffectView` blending within the window, with AppKit's material of that name, such as `headerView`, `titlebar` or `menu`.

### The list header

A track list's header takes its layout from Spotify's album and playlist pages, so it reads the way people know, and its look from the artist page (`src/app/list_header.odin`). It is part of the list's scroll view, so it scrolls with the rows. At the top is the hero on the window's background: the cover, 160 to 232 pt (a fifth of the main view's width) with a shadow, drawn from one 232 pt texture at any width (see [Covers](tidal-data.md#covers)), and next to it the list's kind in small capitals ("ALBUM", "PLAYLIST" or "TOP TRACKS"), its title in 32 pt bold, cut off with an ellipsis when it doesn't fit, and a line under it, centred down the cover as a group. The line says how many songs the list has and how long they play, as "13 songs, 51 min 2 sec" or "3 hr 20 min" from an hour. For an album it starts with the album's artist, a link, and the album's year. Under the hero are the artist page's pills, a light Play and a dark Shuffle, and More. Play plays the list from the top, or pauses and resumes while a song of the list plays. More is a menu with Play, Shuffle, an album's Go to artist and Copy album, playlist or artist link. Then come the column headings and the rows.

Every part of the header has a fixed height (`List_Header`), so each frame knows where row 0 is before it builds anything (`header_rows_top`). The scroll anchor that keeps the top row in place when the rows change, the benchmarks' offsets and the keyboard's scrolling go by it. Once Play has scrolled under the top of the view, a 50 pt bar in the panel grey with a 40 pt cover, the title and a round light Play, all centred down it, is pinned there, with a copy of the column headings under it, whose line then runs the whole width. The hero keeps the room for Back and Forward above its cover, plus 12 pt. The pinned bar is as tall as that room and starts after the pill, so its cover and title sit next to Back and Forward, as a Finder window's title does when its content scrolls. The strip still moves the window, except from the controls under it. How far it has come in is worked out from the scroll offset each frame (`header_collapse`): its background fades in over the 48 pt before the hero's bottom reaches it, Play and the title over the 24 pt before the headings reach it, and then the headings pin. Nothing animates by itself, so a still window draws nothing. The bar is built after the rows, so it is drawn over them and a click on it stops there. The keyboard scrolls a selected row clear of it. The hero and the buttons are built only while some of them are in view; above that a spacer of their height stands in.

An album ends in a footer: its release date, its length, and a shelf of more by its artist, its other albums, whose View all opens the artist's Albums grid. When an album opens, its first song's first artist's page goes in the artist cache, which is asked only for its albums, EPs and singles; the release date and the year come from the album's card there. Copyright isn't shown, since the album's tracks don't carry it and the album itself isn't fetched. Search results use the same header with their own parts (`search_list_header`): the hero is "Results for" the query in 28 pt bold and what was found, and the actions are the tabs. The search field sits in the room at the top, so the pinned bar there is only the panel grey fading in behind Back, Forward and the field, and the tabs pin under it with the headings once they reach it (`List_Header.pin_actions`). The albums, artists and playlists found scroll under the same header and pin the tabs without headings.

### The artist page

Every way to open an artist lands on its page (`src/app/artist.odin`, data in `artist_data.odin`): the search's Artists tab, an artist link in a row or the player bar, the track menu's Go to artist, and a card on another artist's Fans also like shelf. The page is one scroll view, its content in a column at most 1280 pt wide, centred. At the top, 340 pt tall, is the artist's picture at 750 px across the whole width, darkened and fading to the window background, with the name and the first three lines of the biography over it. More shows the rest of the biography and Less hides it again. Without a picture, and with the fake data, a gradient from the name's hue stands in. The picture fades in once it arrives, asking for frames only until it's opaque. Under it are Play, Shuffle, Follow, Share and More. Follow, with a plus, follows the artist on TIDAL and turns into Following, with a check, at once; pressed again it unfollows (see [TIDAL data](tidal-data.md#followed-artists)). It's disabled until the followed artists have come from TIDAL. Share copies `https://tidal.com/browse/artist/<id>` (not with the fake data). More is a menu with Play, Shuffle, Show all top tracks and Copy artist link. Play and Shuffle stay disabled until the first top track has loaded.

The top tracks are the open list, the artist's `artists/{id}/toptracks` as a `Track_View` with source `.Artist`, so the list cache keeps them like any list. The page shows its first five rows with the table's own `track_row`, so hearts, the more menu, links, dragging onto a playlist and keyboard play work as in the table. With the five rows focused, the arrow keys move the selection among them and Enter plays it. View all shows the whole list as the table, with the artist's picture in its header.

Each part of the page with cards is a shelf: Albums, EPs and singles, Appears on and Fans also like, in the order of `artist_part_spec`. A shelf is a titled row of cards, 160 pt covers with a title and a subtitle, round for artists. It scrolls sideways with a trackpad, Shift and the wheel, or Left and Right once a card has the focus. When the cards don't fit, ‹ and › by the title page through them by as many whole cards as show. A shelf builds at most 50 cards, all of them focusable, so Left and Right never move to a card that isn't there; the ones out of view are built empty. A part on its way shows its title and grey squares. A part that failed says why, with a Retry. View all shows the whole part, up to 500 cards, as a grid that scrolls down, with the rows out of view not built. The cards are keyed under the grid, not their row, so a resize that changes how many fit in a row keeps the focus and the accessibility ids. Its Back button and Escape go back.

The page, its full top tracks and a shelf's grid are places of their own in the history: `List_Place.artist_view` is nil for the page, `Artist_Top_Tracks` or `Artist_Grid`, and Back and Forward go through them. Moving among the three for one artist keeps the open list, so the top tracks aren't fetched again and a row playing stays lit. What the main view shows is worked out each frame from the history's current place and the open list (`artist_place`): an artist place whose list is open shows the page or the grid. So clicking a sidebar playlist or searching leaves the page with nothing to reset.

The biography breaks into lines at spaces and line breaks. A word wider than the column, such as a link or a paragraph of Chinese or Japanese, which has no spaces, breaks between grapheme clusters (`ui.cluster_bounds`), as many as fit on each line, with their widths from one shaping of the word (`ui.cluster_widths`). The lines are kept with the page as byte ranges into its text, and broken again only when the width, the font, its size, the display scale or the text system's fallback fonts change, or a new biography arrives. More and Less only change how many of them show.

### The Home page

Home is a row of its own at the top of the sidebar, with Phosphor's house: outlined, and filled and lit while Home shows. Search is the same kind of row under it, with the magnifying glass, lit while the search page shows (see [Search](search.md)). Both are `sidebar_nav_row`, above "Your Library". It isn't where the app starts; the app still opens on the sidebar's first entry. The page is in `src/app/home.odin`, one scroll view with its content in the artist page's centred column (`CONTENT_MAX`, `PAGE_PAD`) and the player bar's inset at its end.

At the top is a greeting by the local hour: Good morning from 5 to 12, Good afternoon to 18, Good evening the rest. Under it are the sidebar's first eight entries as shortcut tiles, Liked Songs first: 56 pt tall, the cover at the left and the name next to it, on the surface grey with rounded corners, four to a row when the column is at least 760 pt wide and two otherwise. A click opens that sidebar entry. The tiles share a keyed parent, so the arrow keys move through them as a grid.

Then come the shelves from TIDAL's home feed (see [TIDAL data](tidal-data.md#the-home-feed)), drawn with the artist page's `card_row`: ‹ and › paging, cards built empty out of view, round covers for artists. Home's shelves have no View all. A card opens its album, artist page or playlist through `open_card`. While the first fetch is out the page shows three grey shelves; if it failed with nothing to show, it says why, with a Retry. A feed with no shelves Home can show says "Nothing to show yet", with a Refresh that fetches it again. A refresh keeps the old shelves on screen until the new ones land.

Home is a place in the history (`Home_Place`), so Back and Forward go through it. What the main view shows is worked out from the history's current place (`home_showing`), and the open list stays as it was underneath, so going back from Home to a playlist or an artist page fetches nothing. While Home shows, no sidebar playlist is lit. With `TIDALFAST_FAKE=1` the shelves are made from the fake rows' albums and artists and the fake playlists, with gradient covers.

### The settings page

Settings in the user menu, at the bottom of the sidebar, shows the settings page (`src/app/settings_page.odin`), a place in the history like Home, so Back leaves it. It is laid out after [Hex](https://github.com/anomalyco/hex)'s settings in the app's own greys and accent: a column at most 720 pt wide, centred, with a card per group under the group's name. A card is a panel with a hairline border and 10 pt corners. Each of its rows is 60 pt tall, with the setting's name and a line about it on the left and its control on the right, and a hairline between rows.

- Appearance has the scrollbars' mode, where the renderer has backdrops, the player bar's (see [Scrollbars](playback.md#scrollbars)), and, on Linux where the compositor offers decorations, the title bar (see `docs/linux.md`, The title bar). A setting with a few choices shows them side by side in one control, with the chosen one raised.
- Playback has bit-perfect output, which the output menu also has (see [Output settings](playback.md#output-settings)), as a switch. The knob slides across in the accent (`ui.slide`, which keeps the position in the box's `open_t`) and asks for no frames once it's there. A switch built for the first time starts where it belongs, so the page's first frame shows it settled.
- Account, when signed in, has the user's name and Log out.

Assistive apps get each choice as a button named for what it chooses, such as "Docked scrollbars", selected when chosen, and the switch as a button with the value On or Off.

## Performance

`TIDALFAST_BENCH=1`, release build, Apple M1, 1100×700 window, overlay on. About 10 rows and 1,000 to 1,800 instances in view. ui is everything before `render.end_frame`:

| phase | what | ui avg | ui max |
|---|---|---|---|
| warm | back and forth over rows already built | 0.70 to 0.75 ms | 1.9 ms |
| cold | 3 new rows a frame | 0.94 to 1.16 ms | 3.8 to 5.4 ms |
| jump | a new page every frame | 1.2 to 1.35 ms | 4.3 to 4.8 ms |

With the overlay off, warm is 0.53 to 0.60 ms. Of a warm frame, building the tree takes about 0.13 ms, layout about 0.1 ms, and drawing labels about 0.37 ms (89 labels, so about 4 µs each, inside `text.draw_run` and `render.push`). The cold maximum is the phase's first frame. It jumps 2,000 rows and meets emoji in Medium 14 for the first time. Timed inside `src/text`, that frame spends about 2 ms shaping 40 runs and the rest rasterizing 3 glyphs. Rasterizing the first Apple Color Emoji glyph took 6 ms, and the first line CoreText lays out in Geeza Pro (Arabic) 3.8 ms, against 30 to 200 µs for later lines at any size. The text loader now lays out and draws the character it loaded a fallback face for, on its own thread, which took the cold maximum from 9.3 to 11.9 ms down to 3.8 to 5.4 ms. What remains is per glyph: each emoji glyph costs 0.4 to 2.4 ms to rasterize, decoding its bitmap.

The bench draws frames back to back. A window that redraws a few times a second runs each frame on cold caches and often on the efficiency cores, so the same work takes two to three times as long. Measured that way on 1 November, release build, M1 on battery, fake data, Liked Songs open at 1100×700 and redrawn 15 times a second, with timers and `thread_selfcounts` around each part: building the tree (sidebar, track table, player bar), `begin_frame`, layout, `finish` and `access_build` took about 0.31 ms and 384,000 UI-thread instructions a frame, for 387 boxes. Before the changes that cut the boxes per track row from 27 to 17, merged the layout's ten walks into two, moved the per-frame strings off `fmt.tprintf` and made `begin_frame`'s prune go through the pool instead of every bucket, the same frame took 0.49 ms and 854,000 instructions for 497 boxes. Layout went from 218,000 instructions to 94,000 and `begin_frame` from 32,000 to 3,600. `draw_box` isn't in these numbers.

Drawing, the `draw_box` walk in `end_frame`, was measured on 1 November with a probe around it: release build, fake data, the library view with Liked Songs open at the default window size, redrawing 15 times a second, the UI thread's instructions and cycles from `thread_selfcounts`. A frame visits 482 boxes and draws 85 labels with 803 glyphs into 765 instances. It took 642,000 instructions, of which about 194,000 hashed the 200 instances under the player bar's blur byte by byte, and about 430 went to each glyph. Hashing eight bytes at a time, `push_sprite` for glyphs and packing a run's glyph sizes once brought it to 303,000, about 245 a glyph. At a high clock that was 319,000 cycles (0.11 ms) before and 164,000 (0.05 ms) after. At a low clock it was about 510,000 (0.38 ms) before and 330,000 (0.25 ms) after. Glyphs are about two thirds of what's left. Per glyph, the subpixel split and atlas lookup take about 90 instructions and writing the instance about 100.

Shaping a run costs 60 to 280 µs. Most of it is kb_text_shape, not CoreText: `ShapeRun`, where kb_text_shape applies the font's lookups, took about 2 µs a character with Inter (130 to 170 µs for a 70 character title), and push, begin and end take about 1 µs. kb_text_shape keeps its shape configs in the context, so that isn't set up again per run. For text in morx-only fonts (Arabic in Geeza Pro, emoji) CoreText adds 30 to 200 µs per run in `CTLineCreateWithAttributedString`. Building the CFString and attribute dictionary costs 3 to 20 µs and the CTFont per size is cached.
