# UI

`src/ui` is an immediate-mode UI after Ryan Fleury's box UI in raddebugger. Each frame the app builds a tree of boxes. `end_frame` lays it out, draws it with `render` and `text`, and records where every box landed. The next frame tests input against those rects, so a click goes to what was on screen.

```odin
ui.begin_frame(&s.ui, events, r, &s.text, w, h, time, input.mouse_buttons)
{
	ui.row("body", {}, ui.fill(), ui.fill())          // parent until the end of the scope
	ui.label("Your Library", ui.text_size(), ui.px(52))
	if ui.button("Play##play").clicked { play() }
}
animating := ui.end_frame()                             // goes to the shell as Frame_Result.animating
```

## Boxes and keys

A box built with an ID string is keyed by an FNV-1a hash of the string, seeded with the key of its nearest keyed ancestor, so `"##row12"` in two lists gives two keys. `"Play##row12"` shows "Play" and hashes the whole string. `"Pause###play"` hashes only `"###play"`, so a label can change without the box losing its state. Keyed boxes come from a pool of 8,192 in the persistent arena, found through a 4,096-bucket chained hash table, with a free list. Each one keeps its rect, clipped rect, content size, scroll offset and animation values. `begin_frame` frees every box that wasn't built in the previous frame. A box with no ID (`ui.label`, spacers) lives in the frame arena for one frame and has no state. A key built twice in one frame makes the second box keyless instead. When the pool is full, new keyed boxes come from the frame arena with key 0 and keep no state. The UI logs that when it starts, at most once a second, and the overlay's last line turns red with the number of boxes that missed out.

`State` and every box are plain data: pointers into the persistent arena and the frame arena, no procedure pointers. The renderer and text pointers and the tree are set again by `begin_frame`, and the package keeps its current `State` in a thread-local pointer that `begin_frame` sets, so a hot reload carries the UI over. Strings given to boxes must live until `end_frame`. That holds for literals, the persistent arena and `fmt.tprintf`.

## Sizes and layout

Each box has a size per axis: `px(n)`, `text_size(pad)` (the label's width or line height plus `pad`), `pct(f)` of the nearest ancestor with a size of its own, or `children_sum()`. `fill()` is `pct(1, 0)`. Each size has a strictness: how much of it the box keeps when its parent has too little room. `layout.odin` runs Fleury's five passes per axis: standalone sizes (pixels, text), upwards-dependent (percentages, skipping ancestors sized by their children), downwards-dependent (children sums), violations, then positions. The violations pass runs from the root down, and before it solves a box's children it takes their percentages again from the box's final size. Without that, a `fill()` inside a `fill()` that its parent shrank kept the outer one's first size, and a strict `pct(f, 1)` inside it, like the progress bar's fill, came out as a share of the whole window. When the children along a box's child axis don't fit, each gives up `size * (1 - strictness)` in proportion until the overflow is gone. Across the axis a child larger than its parent is cut to fit. Scroll views allow overflow on their scroll axis and skip that step. A box's `gutter` comes off its width before its children get any; a docked scrollbar uses it. A box with `Floating_X`/`Floating_Y` sits at `fixed_pos` outside the flow. So a row of `px(44)`, `fill()` and `px(56)` gives the middle box whatever is left.

## Input

`process_events` folds the frame's events into `Input` and walks them in order. The hit list from the last layout holds every keyed box that is clickable, focusable or scrolls, with its clipped rect, in drawing order. The hot box is the last clickable one under the mouse, so children beat parents and the floating layer beats everything. A press makes the hot box active for that button and clicks it. A box with `Click_On_Release` clicks on a release over it instead, so a drag can start from it without the click firing. The links in the track table have it, since a drag from them drags the row. While the left button is held only the active box can be hot. `ui.signal(box)` reports hovering, held, pressed, released, clicked, double-clicked (from the shell's click count), right-clicked (on mouse down, as macOS menus do, control-click included), dragging (past 4 pt, until the release) with the drag delta, and scroll. `Signal.mouse` is the current mouse while held and where the button came up when released, and the drag delta runs to the release too. A press and release in one frame, which happens when the events arrive between two frames, still reports both, so sliders and handles act on `held || released` with `Signal.mouse` rather than on `held` alone. `Input` keeps where each button last went down and came up.

A release can go missing, as when the mouse comes up in another app after the window lost focus. So the app passes `Frame_Input.mouse_buttons` to `begin_frame`. The shell fills it every frame with the buttons down in the whole session, which on macOS it asks CoreGraphics for (`CGEventSourceButtonState`). A button held since an earlier frame that is up in hardware, with no event for it this frame, gets one more frame for its release to arrive, and then the UI lets go of it: no release, no click from a release, and a drag it held ends without a drop. A hot reload lets go of every button the same way (`ui.cancel_pointer`). Without the hardware state, as in the tests, the UI goes by the events alone.

A clickable box also counts as hovering while its clickable child is hot, so a row stays lit under its own "more" button.

Keyboard: Tab and Shift-Tab move the focus through focusable boxes in drawing order, starting at the first or last when nothing has it. The arrows move it to the nearest focusable box with the same keyed parent in their direction: past the focused box along the arrow's axis and overlapping it across. So Up and Down move along a column, Left and Right along a row of cards, and all four through a grid of them. With no box overlapping it that way, an arrow goes to the nearest box that way at all, so a box off to the side is still reached. Right from Forward in the sidebar reaches Settings, and Down into a grid's short last row reaches its last card. A box with nothing that way, or a text field with the focus, leaves the key to the field or to `ui.take_key`. A list that moves a selection with the arrows needs a keyed parent of its own, as the artist page's top tracks have, so no other box in its group takes the keys first. Enter and Space click the focused box (`Signal.keyboard` says it came from a key). Escape cancels a drag, or else closes the menu, or else drops the focus. When the keyboard moves the focus, the scroll views around the focused box scroll the least it takes to show it, along each axis the nearest one that scrolls that way. So a card in a sideways row inside a page that scrolls down comes into view across and down. A box larger than the view, like the track table, doesn't scroll while any of it shows, so Tab into the table keeps the reader's place; out of view, its nearer end comes in. A press moves the focus to the box clicked, or its nearest focusable ancestor. Keys the UI doesn't use wait in a list for `ui.take_key(code, modifiers)`. Focus from the keyboard draws a ring; focus from a click doesn't.

## Scrolling

Each axis scrolls on its own. A scroll goes, along each axis, to the innermost scroll view under the mouse that allows overflow that way. So a row that scrolls sideways inside a page that scrolls down takes the sideways part of a diagonal trackpad scroll, and the page takes the rest. A wheel with no sideways delta over the row scrolls the page. A trackpad gesture keeps both of its views until the next gesture, momentum included. A mouse wheel scrolls whatever is under the mouse. Trackpad deltas move the view straight away. macOS sends the momentum phase as more deltas, so the UI adds no inertia of its own. Wheel lines (16 pt each) move a target that the view eases toward. Both are clamped to the content size from the last layout while building, then again to the layout just done, since the content may have shrunk. `ui.virtual_rows(view, count, row_h)` builds only the rows in view, `floor(offset / row_h)` to `ceil((offset + height) / row_h)`, plus one row past each edge so the keyboard can move onto it, with a spacer above and below for the rest. Its `start` is where row 0 sits in the content, for rows under a header that scrolls with them; the rows can then go in a box of their own inside the view. A row that isn't built has no box, so a focused row scrolled out of view loses the focus. The sidebar's playlists are built this way, and a focused playlist scrolled away by the wheel or the trackpad is no longer focused when it comes back.

## Animation and redraws

`hot_t`, `active_t`, `focus_t`, `open_t` and the scroll offset ease toward their targets with `v += (target - v) * (1 - exp(-dt * k))`. The step is capped at 1/30 s, so the first frame after a long idle doesn't jump to the end. A value within its epsilon snaps to the target. Anything still moving sets `animating`, which `end_frame` returns and the app passes to the shell. A new keyed box asks for one more frame, since it has no rect to test input against yet, and so does a hot box that changed under a still mouse. So does a scroll view whose layout didn't match what its children were built for: its size changed (a taller window needs more virtual rows) or its offset had to be clamped (the content shrank). The next frame builds it right. At most 3 such frames come in a row, so a layout that never settles can't keep the window drawing. The count starts over in a frame with events or a new window size, and when the app calls `ui.data_changed()`, so the limit only stops retries with nothing new coming in. Tooltips keep frames coming during their half-second delay. Once everything settles, no more frames are asked for and the window goes back to 0% CPU.

## Floating layer

`ui.floating()` makes a second root the parent until the end of the scope. It is laid out after the main tree, drawn after it with no clip from it, and its boxes come last in the hit list, so they get input first. Menus, tooltips and the drag ghost live there. `ui.open_menu(id, pos)` opens a context menu and `if ui.menu(id) { ui.menu_item(...) }` builds it while it's open or fading out. The deferred end of `ui.menu` runs at the end of the `if`, so the items must go inside its block. Opening it moves the focus to its first item. While it's open, Tab and the arrows move only among its items and Enter and Space click only them, and closing it puts the focus back where it was. A left click outside the menu closes it and goes no further; a right click closes it and goes on, so it can open another. A menu fading out takes no input, and neither does one that closed while it was being built, as when an item was clicked: its boxes stay out of the hit list. A menu flips above the mouse when there's no room below. `ui.tooltip(signal, text)` shows text by the mouse once the box has been hovered for 0.5 s.

## Drag and drop

A source calls `ui.drag_begin(payload)` once its signal says dragging. From then on the UI owns the drag: any left release ends it, wherever the mouse is and whether or not the source box is still built, and Escape cancels it. Moving on with the button still held after Escape doesn't start a new one. `ui.drag_payload()` reports the drag while it goes on, for drawing a ghost. A target calls `ui.drop_hover(box)` to light up and `ui.dropped(box)`, which returns the payload in the frame a drag ends over the box. A drag that goes down, past 4 pt and up between two frames still drops: its source's signal says dragging and released, `drag_begin` takes it, and since targets built before the source have already asked, `dropped` returns it in the next frame, tested against the rects it was released over. The release asks for that frame.

## Drawing

Box flags pick what's drawn, in this order: shadow, background (optionally a vertical gradient), the hover and press overlays faded by `hot_t` and `active_t`, border, focus ring, label, then the children inside the box's clip if it has `Clip`. `opacity` multiplies the box and everything in it. A label is centred vertically, aligned left, centre or right inside `text_pad`, and truncated with an ellipsis to the box's width. A box whose clipped rect is empty draws nothing itself. Labels are shaped when drawn, through the text cache, unless the box is sized by its text, in which case layout shapes it first. Nothing in the UI allocates outside the frame arena after `ui.init`.

## The library screen

`src/app/library.odin` follows spotifast's layout, in neutral greys with a cyan (#00ffff) accent: a sidebar of 32 fake playlists, 250 pt wide by default, resized with a 5 pt handle between 210 and 600 pt (it stops growing once the main view would go below 360 pt). Next to it is the main view with the list's header and the 10,000-row track table (see [The list header](#the-list-header)), and the 88 pt player bar runs along the bottom. A row at the top of the sidebar, above "Your Library", has Back and Forward, which go through the last 50 places visited (`History` in `library.odin`): sidebar playlists, albums, artist pages, an artist's full top tracks and shelf grids, playlists from search, and searches. A TIDAL playlist is found again by its id, so Back still opens it after the sidebar changes order, and opens Liked Songs once it's gone. A search typed a letter at a time is one place, so Back from a list opened in the results shows the results for the final query, with the query back in the field. Rows are 56 pt. The columns follow spotifast's `columns`, measured on the main view's width, and the list's kind (`List_Kind`) picks them in `track_columns`: # and title always, and the cover always but on an album, whose rows are all the same album. Album shows above 560 pt (28% of the width, 140 to 360 pt), again not on an album, and date added above 760 in playlists and Liked Songs. Albums, artists and search results have no date added, so they never show it. Duration and the "more" button always show. Between date added and duration is the heart column: a filled heart in the accent when the track is liked, an outline otherwise, shown when the row is hovered or selected like the "more" button. A click turns the heart at once (see [TIDAL data](tidal-data.md)) and selects the row. Hovering lights a row; a click selects it; a double-click plays it (see [Playback](playback.md)), and the row playing is lit. The queue remembers which list it came from (its kind and TIDAL id, or the search query), so the row stays lit after going to another list and back, and the same track in another list isn't lit. When the reopened list's rows differ, the first row with the playing track's id is lit. A row's artists and album are links: clicking one opens that artist's page or that album, the same places as Go to artist and Go to album. Each of a song's artists is its own link, with the commas between them as plain text. A row keeps every artist's id and where its name sits in the joined artist string (`Artist_Ref`), so a name with a comma in it, like "Tyler, The Creator", stays one link. A link is only as wide as its text and is underlined while the mouse is over it (`ui.link`). When the artists don't fit, the one that crosses the edge ends in an ellipsis and the rest are left out. This goes by the width from the last layout, and the box clips, so the frame after a resize never draws past it. Pressing, right-clicking or dragging on a link does the same as on the rest of the row. In the player bar, the title opens the playing track's album and each artist opens that artist. A heart right after the title likes or unlikes the playing track. Rows without an album or artist id show plain text. A right click or the "more" button opens a context menu with Play, Go to album, Go to artist and Copy song link (see [Search](search.md)). Dragging a row onto a playlist shows a ghost and a drop highlight, and dropping it adds the track on TIDAL, or likes it on Liked Songs (see [TIDAL data](tidal-data.md#the-list-cache)). The drag goes through `ui.drag_begin` with the row index, so releasing after the row has scrolled out of view still ends it. With the table focused, the arrow keys, Page Up/Down and Home/End move the selection and scroll it into view, and Enter plays it. The player bar has shuffle, previous, play/pause, next and repeat, with Phosphor icons (see [Text](text.md)). Shuffle and repeat light in the accent colour with a dot under them while on, and repeat shows a 1 on repeat one. There's a progress bar that seeks on click or drag and shows the drag position while held, elapsed and remaining time, and the volume slider. The times and the table's Time column are as wide as the widest value their pattern can show, measured with the font's widest digit, so they're never cut off; the progress bar and the volume slider take what's left. Rows whose page hasn't arrived yet show their number and grey bars. With `TIDALFAST_FAKE=1` the 32 playlists and 10,000 rows are the fake data again and covers are gradients.

### The status bar

`TIDALFAST_STATUS_BAR=1` adds a 22 pt line under the player bar, for agents that check the app through captures and the accessibility tree. It says whether a track is playing, paused or ended, its title and artist, and then the status (`status_text`: a copied link, an add to a playlist, a list's error, TIDAL's rate limit), as "Playing Song by Someone · Added Song to A playlist", or "Nothing playing". It's a static text in the accessibility tree. The views show neither anywhere else, except errors, which also get a toast.

### The error toast

An error shows in a toast centred over the bottom of the views, 16 pt above the player bar (`src/app/toast.odin`): TIDAL's rate limit with its countdown, a list that failed to load, a failed search, a failed add to a playlist, and `Data.message` (the sidebar, following, the settings, the Keychain). `current_error` picks the most pressing one, and the status bar's text comes from it too. A toast stays 6 s (`TOAST_SECONDS`), longer while the mouse is on it, and a click dismisses it. An error counts as new when its source or text changes, except the rate limit, whose countdown changes every second. The toast asks for a frame at the time it should hide with `ui.wake_at`, and once a second during a rate limit, so it keeps no frames coming while it waits. Playback errors stay in the player bar under the title. Copied links and successful adds show only in the status bar. Without the variable the bar isn't built.

### The window on macOS

The window has no titlebar of its own: the shell hides the title, makes the titlebar transparent and puts the view under it, so only the close, minimise and zoom buttons stay. Each frame it passes the titlebar's height and where the zoom button ends (`Frame_Input.titlebar_height` and `titlebar_inset`, both 0 in full screen and on Linux). The sidebar's top row is that tall and starts Back and Forward 12 pt after the zoom button; elsewhere it is 32 pt with Back 10 pt in. The main view and the login screen start with an empty strip of the same height. On the artist page and over a track list the header runs up under the titlebar instead, that much taller, and the strip floats over it without a background (`hero_under_titlebar`), unless the login notice is above it. The search results and an artist's grids keep the strip above them. Boxes flagged `Window_Drag` (that strip and the empty parts of the sidebar's row) go to the shell through `Shell.set_drag_regions`. A press there moves the window, and a double-click zooms or minimises it as System Settings says. `Metal_View` returns NO from `mouseDownCanMoveWindow`, so a press anywhere else in the strip reaches the app.

The sidebar, the main view and the player bar are opaque. An earlier version had an `NSVisualEffectView` behind the window, showing the blurred desktop through a translucent sidebar or player bar, and dropped it: next to the player bar's own blur of the views it looked worse, and the window has to be composited with alpha for it.

Where the renderer has backdrops (`render.BACKDROPS`, only Metal so far), the player bar floats over the bottom of the window, and the sidebar, the track list, the search results, the grids and the artist page run under it (`bar_inset`, a scroll view's `inset_end`, so their ends still scroll clear of it and the scrollbar stops above it). Its background is a `Draw_Backdrop` box: a blur of the views under it reaching `BAR_BLUR` (20 pt), its colours saturated by `BAR_SATURATION` (1.8), under `BAR_TINT`, the panel grey at 75%, like a macOS material (see [Renderer](renderer.md#backdrops)). The bar is clickable, so a press on its empty parts doesn't reach the row under it. On Linux, or with the Solid player bar in Settings (`Settings.bar`), the bar sits under the views.

`TIDALFAST_BLUR_REFERENCE=<material>[,<height>]` shows AppKit's blur to compare with. The app leaves the bar out, the views still running under where it goes. The shell covers the bottom `<height>` points (88 by default) with an `NSVisualEffectView` blending within the window, with AppKit's material of that name, such as `headerView`, `titlebar` or `menu`.

### The list header

A track list's header takes its layout from Spotify's album and playlist pages, so it reads the way people know, and its look from the artist page (`src/app/list_header.odin`). It is part of the list's scroll view, so it scrolls with the rows. At the top is the hero on the window's background: the cover, 160 to 232 pt (a fifth of the main view's width) with a shadow, and next to it the list's kind in small capitals ("ALBUM", "PLAYLIST" or "TOP TRACKS"), its title in 32 pt bold, cut off with an ellipsis when it doesn't fit, and a line under it. The line says how many songs the list has and how long they play, as "13 songs, 51 min 2 sec" or "3 hr 20 min" from an hour. For an album it starts with the album's artist, a link, and the album's year. Under the hero are the artist page's pills, a light Play and a dark Shuffle, and More. Play plays the list from the top, or pauses and resumes while a song of the list plays. More is a menu with Play, Shuffle, an album's Go to artist and Copy album, playlist or artist link. Then come the column headings and the rows.

Every part of the header has a fixed height (`List_Header`), so each frame knows where row 0 is before it builds anything (`header_rows_top`). The scroll anchor that keeps the top row in place when the rows change, the benchmarks' offsets and the keyboard's scrolling go by it. Once Play has scrolled under the top of the view, a 64 pt bar in the panel grey with a 40 pt cover, the title and a round light Play is pinned there, with a copy of the column headings under it. How far it has come in is worked out from the scroll offset each frame (`header_collapse`): its background fades in over the 48 pt before the hero's bottom reaches it, Play and the title over the 24 pt before the headings reach it, and then the headings pin. Nothing animates by itself, so a still window draws nothing. The bar is built after the rows, so it is drawn over them and a click on it stops there. The keyboard scrolls a selected row clear of it. The hero and the buttons are built only while some of them are in view; above that a spacer of their height stands in.

An album ends in a footer: its release date, its length, and a shelf of more by its artist, its other albums, whose View all opens the artist's Albums grid. When an album opens, its first song's first artist's page goes in the artist cache, which is asked only for its albums, EPs and singles; the release date and the year come from the album's card there. Copyright isn't shown, since the album's tracks don't carry it and the album itself isn't fetched. Search results have no hero and no bar; their headings pin as soon as the list scrolls.

### The artist page

Every way to open an artist lands on its page (`src/app/artist.odin`, data in `artist_data.odin`): the search's Artists tab, an artist link in a row or the player bar, the track menu's Go to artist, and a card on another artist's Fans also like shelf. The page is one scroll view, its content in a column at most 1280 pt wide, centred. At the top, 340 pt tall, is the artist's picture at 750 px across the whole width, darkened and fading to the window background, with the name and the first three lines of the biography over it. More shows the rest of the biography and Less hides it again. Without a picture, and with the fake data, a gradient from the name's hue stands in. The picture fades in once it arrives, asking for frames only until it's opaque. Under it are Play, Shuffle, Follow, Share and More. Follow, with a plus, follows the artist on TIDAL and turns into Following, with a check, at once; pressed again it unfollows (see [TIDAL data](tidal-data.md#followed-artists)). It's disabled until the followed artists have come from TIDAL. Share copies `https://tidal.com/browse/artist/<id>` (not with the fake data). More is a menu with Play, Shuffle, Show all top tracks and Copy artist link. Play and Shuffle stay disabled until the first top track has loaded.

The top tracks are the open list, the artist's `artists/{id}/toptracks` as a `Track_View` with source `.Artist`, so the list cache keeps them like any list. The page shows its first five rows with the table's own `track_row`, so hearts, the more menu, links, dragging onto a playlist and keyboard play work as in the table. With the five rows focused, the arrow keys move the selection among them and Enter plays it. View all shows the whole list as the table, with the artist's picture in its header.

Each part of the page with cards is a shelf: Albums, EPs and singles, Appears on and Fans also like, in the order of `artist_part_spec`. A shelf is a titled row of cards, 160 pt covers with a title and a subtitle, round for artists. It scrolls sideways with a trackpad, Shift and the wheel, or Left and Right once a card has the focus. When the cards don't fit, ‹ and › by the title page through them by as many whole cards as show. A shelf builds at most 50 cards, all of them focusable, so Left and Right never move to a card that isn't there; the ones out of view are built empty. A part on its way shows its title and grey squares. A part that failed says why, with a Retry. View all shows the whole part, up to 500 cards, as a grid that scrolls down, with the rows out of view not built. The cards are keyed under the grid, not their row, so a resize that changes how many fit in a row keeps the focus and the accessibility ids. Its Back button and Escape go back.

The page, its full top tracks and a shelf's grid are places of their own in the history: `List_Place.artist_view` is nil for the page, `Artist_Top_Tracks` or `Artist_Grid`, and Back and Forward go through them. Moving among the three for one artist keeps the open list, so the top tracks aren't fetched again and a row playing stays lit. What the main view shows is worked out each frame from the history's current place and the open list (`artist_place`): an artist place whose list is open shows the page or the grid. So clicking a sidebar playlist or searching leaves the page with nothing to reset.

The biography breaks into lines at spaces and line breaks. A word wider than the column, such as a link or a paragraph of Chinese or Japanese, which has no spaces, breaks between grapheme clusters (`ui.cluster_bounds`), as many as fit on each line, with their widths from one shaping of the word (`ui.cluster_widths`). The lines are kept with the page as byte ranges into its text, and broken again only when the width, the font, its size, the display scale or the text system's fallback fonts change, or a new biography arrives. More and Less only change how many of them show.

### The Home page

Home is a row of its own in the sidebar, under Back and Forward and above "Your Library", with Phosphor's house: outlined, and filled and lit while Home shows. It isn't where the app starts; the app still opens on the sidebar's first entry. The page is in `src/app/home.odin`, one scroll view with its content in the artist page's centred column (`CONTENT_MAX`, `PAGE_PAD`) and the player bar's inset at its end.

At the top is a greeting by the local hour: Good morning from 5 to 12, Good afternoon to 18, Good evening the rest. Under it are the sidebar's first eight entries as shortcut tiles, Liked Songs first: 56 pt tall, the cover at the left and the name next to it, on the surface grey with rounded corners, four to a row when the column is at least 760 pt wide and two otherwise. A click opens that sidebar entry. The tiles share a keyed parent, so the arrow keys move through them as a grid.

Then come the shelves from TIDAL's home feed (see [TIDAL data](tidal-data.md#the-home-feed)), drawn with the artist page's `card_row`: ‹ and › paging, cards built empty out of view, round covers for artists. Home's shelves have no View all. A card opens its album, artist page or playlist through `open_card`. While the first fetch is out the page shows three grey shelves; if it failed with nothing to show, it says why, with a Retry. A feed with no shelves Home can show says "Nothing to show yet", with a Refresh that fetches it again. A refresh keeps the old shelves on screen until the new ones land.

Home is a place in the history (`Home_Place`), so Back and Forward go through it. What the main view shows is worked out from the history's current place (`home_showing`), and the open list stays as it was underneath, so going back from Home to a playlist or an artist page fetches nothing. While Home shows, no sidebar playlist is lit. With `TIDALFAST_FAKE=1` the shelves are made from the fake rows' albums and artists and the fake playlists, with gradient covers.

## Performance

`TIDALFAST_BENCH=1`, release build, Apple M1, 1100×700 window, overlay on. About 10 rows and 1,000 to 1,800 instances in view. ui is everything before `render.end_frame`:

| phase | what | ui avg | ui max |
|---|---|---|---|
| warm | back and forth over rows already built | 0.70 to 0.75 ms | 1.9 ms |
| cold | 3 new rows a frame | 0.94 to 1.16 ms | 3.8 to 5.4 ms |
| jump | a new page every frame | 1.2 to 1.35 ms | 4.3 to 4.8 ms |

With the overlay off, warm is 0.53 to 0.60 ms. Of a warm frame, building the tree takes about 0.13 ms, layout about 0.1 ms, and drawing labels about 0.37 ms (89 labels, so about 4 µs each, inside `text.draw_run` and `render.push`). The cold maximum is the phase's first frame. It jumps 2,000 rows and meets emoji in Medium 14 for the first time. Timed inside `src/text`, that frame spends about 2 ms shaping 40 runs and the rest rasterizing 3 glyphs. Rasterizing the first Apple Color Emoji glyph took 6 ms, and the first line CoreText lays out in Geeza Pro (Arabic) 3.8 ms, against 30 to 200 µs for later lines at any size. The text loader now lays out and draws the character it loaded a fallback face for, on its own thread, which took the cold maximum from 9.3 to 11.9 ms down to 3.8 to 5.4 ms. What remains is per glyph: each emoji glyph costs 0.4 to 2.4 ms to rasterize, decoding its bitmap.

Shaping a run costs 60 to 280 µs. Most of it is kb_text_shape, not CoreText: `ShapeRun`, where kb_text_shape applies the font's lookups, took about 2 µs a character with Inter (130 to 170 µs for a 70 character title), and push, begin and end take about 1 µs. kb_text_shape keeps its shape configs in the context, so that isn't set up again per run. For text in morx-only fonts (Arabic in Geeza Pro, emoji) CoreText adds 30 to 200 µs per run in `CTLineCreateWithAttributedString`. Building the CFString and attribute dictionary costs 3 to 20 µs and the CTFont per size is cached.
