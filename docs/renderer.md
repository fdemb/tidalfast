# Renderer

`src/render` draws everything as instances of one quad. Each instance is a rounded box drawn with a signed distance function in the fragment shader. It has four corner colours, four corner radii, a border width, an edge softness, a clip rect, and an optional texture with a source rect. A shadow is a soft-edged box drawn under the real one (`push_shadow`).

One blend state covers every instance: premultiplied over, `src + dst * (1 - src.a)`. An instance with the `Additive` flag writes its `extra` as the alpha instead, so the blend gives `dst * (1 - extra) + colour`. With `extra` 0 that adds the colour to what's under it, as macOS's plus-lighter does, without a second pipeline.

`push_rim` uses it for a stroke just inside a cover's edge, with white at `lift` as the colour and `darken` as `extra`. Each channel under it moves toward `lift / darken` in linear light. Covers use 0.025 for both, which is white at 2.5% over the cover: every edge gets a little lighter and keeps the cover's hue. A dark green edge goes from (55, 99, 20) to (71, 107, 50), a light yellow one from (229, 227, 80) to (230, 228, 90), so the rim shows on dark covers and fades out on light ones. It is 1 pt wide, 2 pixels at 2x. An earlier rim was one physical pixel with a lift of 0.03 and a darken of 0.25, which darkened light covers' edges; the plain lighter stroke looked better.

The API takes points. The renderer multiplies by the backing scale and rounds rect edges, clip rects and borders to whole pixels, so a 1 pt border is exactly 2 pixels at 2x. Glyphs already lie on whole pixels, so text draws them with `push_sprite`. It takes pixel edges and a source rect and writes the same instance `push_image` would, without converting to points and rounding back. Glyphs are most of a frame's instances, and this took about 120 instructions off each.

Colours are sRGB with straight alpha, as a design tool shows them. The drawable is `BGRA8Unorm_sRGB`, so the GPU blends in linear space. The shader interpolates gradient colours in premultiplied sRGB, which matches CSS gradients, then converts to linear before blending. Glyph coverage blends in linear space the same way.

Textures come from `texture_create`, `texture_update` and `texture_destroy`. A `Texture` handle carries a generation, so a stale handle draws solid colour. The zero handle is a 1x1 white texture and means "no texture". Formats:

- `R8` is linear coverage for the glyph atlas. The texture swizzle makes it sample as premultiplied white.
- `RGBA8` and `BGRA8` take sRGB colour with alpha premultiplied in sRGB space. That's what a premultiplied `CGBitmapContext` produces, so CoreGraphics output (emoji, decoded images) goes in as is. Pass `mipmapped = true` for a texture drawn smaller than it is. Every update then regenerates the mips.

Colour textures are stored as `_sRGB` formats, and the GPU decodes sRGB before it filters. Uploading premultiplied sRGB bytes directly would decode `alpha * c` instead of giving `alpha * decode(c)`, which makes every translucent texel too dark: 50% white over black came out as 128 instead of 188. So each translucent texel is rewritten as the sRGB encoding of its premultiplied linear colour, `encode(decode(c / a) * a)`. The sample is then premultiplied linear, the same thing the shader makes from a solid colour, and filtering and mipmapping average the right values. Opaque and fully transparent texels don't change, so opaque cover art costs only a scan. The test screen has a black strip with 50% white three ways (an `RGBA8` texel, an `R8` texel and a solid rect), and all three read 188 in a capture.

The rewrite is `convert_premultiplied`, which works in place and touches no renderer state, so a decode worker can run it and pass `converted = true` to `texture_update`. Otherwise `texture_update` runs it on a copy when some texel is translucent. It reads a 256×256 table indexed by alpha and channel byte, built at start; a test checks all 65,536 entries against the formula. A 2048×2048 texture with every texel translucent now takes 7 ms to convert and upload with mips, down from 216 ms, in an optimized build (179 ms, from 893 ms, in debug).

`texture_update` writes on the CPU straight away. A mipmapped texture remembers the command buffer of its last mip generation, which reads the whole base level, and the next write waits for it. The glyph atlas has no mips, so its writes never wait.

Batching: a draw call binds two textures, one colour (`RGBA8` or `BGRA8`) and one coverage (`R8`), and an instance flag says which one it samples. Solid instances don't sample, so they join whatever batch is open. A new draw call starts only when a textured instance needs a texture of its kind other than the one the batch already binds. So a list of covers from one page with their labels in the glyph atlas is one draw call. The mock's library took 37 draw calls a frame when each cover and the label next to it broke the batch, and takes 3 now. Clipping is per instance: the vertex shader cuts the quad down to the clip rect, so changing the clip never breaks a batch.

## Backdrops

`push_backdrop` fills a rect with a blur of what was pushed before it, the way a macOS material blurs the content scrolling under a bar. It always opens a batch of its own, so the batches before it are exactly what it blurs. `end_frame` then draws in two parts in one command buffer. First those batches go to the scene texture, at half size, covering only the rect plus the blur's reach (clamped to the drawable): the vertex shader takes the target's origin and size in the drawable, and the fragment shader maps the target's pixels back to the drawable's, so instances keep their coordinates. Drawing it at half size is the first halving of the blur, at a quarter of the fill. Then a dual Kawase filter (Bjorge, 2015) halves it `levels - 1` more times into `RGBA16Float` textures and adds it back up to a quarter of the region, about doubling the reach with each level, so `levels` is about log2 of the reach in pixels over 2. Last the whole frame draws to the drawable as before, batches before the backdrop included, and the backdrop's instance samples the blurred texture through its `src`, pulls the colour away from its luminance by its saturation (`extra`) and puts its tint over it. The blur keeps its premultiplied alpha, so what was translucent under the backdrop stays a little translucent through it. The scene is in the drawable's sRGB format, so the blur averages linear light, and the float levels keep the dark gradients from banding.

`push_backdrop` also hashes what the blur reads: the instances before it that reach into the region, their batches' textures, the levels, the scale and the clear colour (`backdrop_hash`). It hashes the instances eight bytes at a time (`hash_words`): byte by byte with `fnv64a` it took about 190,000 instructions a frame for the 200 instances under the player bar, a third of drawing the library view. The backend keeps the last blur and draws none of the first part while the hash stays the same. So a frame that only moves the player's progress bar, which is over the blur, costs what it did without one, and only scrolling or a change under the bar blurs again. With the player playing in the fake data, 23 of 90 frames blurred, in the hover and press around starting it.

Every pass is a render pass of its own, and on an Apple GPU each has a fixed cost on top of its pixels, more so at the low clocks a light load runs at. A frame that blurs adds the scene pass and `2 * levels - 3` small passes, 5 for the player bar. At 1100 by 700 pt on a 2x screen its region is 2200 by 216 pixels (88 pt and 20 pt of reach above it), so the scene is 1100 by 108: 0.5 MB, and the levels about 0.3 MB, made once for a size and remade when it changes. One backdrop a frame; another draws its tint.

The Vulkan backend does the same in the frame's command buffer, ahead of the swapchain's render pass. The scene and the levels each have a render pass of their own, `scene_pass` in the swapchain's sRGB format and `blur_pass` in `R16G16B16A16_SFLOAT`. Both draw the whole image, so they start from an undefined layout and end ready to sample. Each pass first waits for the earlier reads and writes of its image in the queue, then makes its writes visible to the fragment shaders after it. That lets one set of images serve all three frames in flight, as on Metal. A pipeline only works with a compatible render pass, and the scene pass's dependencies differ from the swapchain pass's, so the rect pipeline is built twice, once for each. The shaders are `blur.vert`, `blur_down.frag` and `blur_up.frag` in `src/render/shaders`, ports of Metal's. Under the Khronos validation layer with synchronization checks, the Linux build draws the player bar at 820, 1100 and 1600 pt with no errors.

## Glass

`push_glass` draws a lens, as Apple's Liquid Glass does for controls. The player bar's play button is one. It is a single instance with the `Glass` flag, and the fragment shader does all of it, so it costs one quad and no pass of its own. The rim is a quarter circle in profile, `bevel` points wide. Across it the shader moves where it samples outward along the edge's normal, up to `refraction` points at the edge, so what's under the lens bends at its rim. It samples three times, a little further for blue than for red, which splits the colours at the edge as real glass does. A light from the top left catches the rim: a line one point wide, brightest facing the light, half as bright on the far side, with a softer glow inside it. The side away from the light is a little darker. `glow` adds a light around `glow_at`, which the UI sets to the pointer while the button is pressed.

The Instance struct has no fields for these, so the Glass branch reads numbers from the colours: `colors[0]` is the tint, `colors[1]` the backdrop's tint, `colors[2]` the refraction, bevel, highlight and glow, and `colors[3]` where the glow is, its radius and the rim line's width, in pixels.

What the lens bends is the frame's backdrop. A lens inside the backdrop's rect samples its blurred texture with the backdrop's tint and saturation, rebuilding what the backdrop shows there, and gets the `Backdrop` flag too. It comes after the backdrop's batch, so it doesn't change the backdrop's hash and moving it doesn't blur again. A lens anywhere else, or in a frame without a backdrop, has nothing to bend and draws its tint and light over what's under it.

In the UI it's the `Draw_Glass` box flag, tinted by the box's background. Hovered, the light gets stronger. Pressed, the lens grows 6% and lights up under the pointer. Both follow `hot_t` and `active_t`, which settle, so a still button asks for no frames.

## Tilt

`push_tilt` draws a cover that leans under the pointer: the cards' covers and a list's big one, while hovered. Like the lens it is one instance, with the `Tilt` flag, and the fragment shader does all of it from the pointer and one amount, 0 to 1, which the UI eases in and out (`cover_art`, `ui.slide`). The box is a plane seen from two and a half sides away. It comes 4% nearer and tips about its centre by up to 3 degrees, away from the eye where the pointer is. Each pixel finds where its ray meets the plane, and the outline, the picture, the rim and the light work from that point, so the rounded corners lean with the picture. The picture stays fixed in the box, as if printed on it: an earlier version also grew it around the pointer, so it slid against the frame as the pointer moved, and that looked like a trick. A soft light sits at the pointer. It mostly multiplies what it's over, so a black cover gets a sheen and not a grey spot, and the rim catches it.

The numbers go in the colours as the lens's do: `colors[0]` and `colors[1]` are the top and bottom colours (a cover without a picture is a gradient), `colors[2]` the pointer, the amount and the rim's lift, and `colors[3]` the rim's width and its darken. The vertex shader makes the quad a little larger for the growth. The effect's sizes are the `TILT_` constants at the top of the shader. All three backends have the branch. A backend without it would set `render.TILT` false, and the UI would draw the cover flat and the settings page leave the switch out. Settings, Cover hover turns it off.

The instance buffer is triple buffered. Each frame writes into one of three shared `MTLBuffer`s and keeps its command buffer. When the slot comes round again, `begin_frame` waits for that command buffer, which has almost always finished already. If a frame pushes more instances than its buffer holds, that slot's buffer doubles, the frame's instances so far are copied over, and the frame keeps going. Each slot keeps its own size, so a slot that grew stays big and the others grow only when they need to.

## What a frame costs outside the UI

Measured on 1 November on an M1 on battery, release build, fake data, the library with a playlist open, a frame every 1/15 s, with instruction counts from `thread_selfcounts` and `proc_pid_rusage`. A frame ran about 1.77 million instructions on the main thread and 0.65 million on other threads.

`render.end_frame` is about 135,000 of the main thread's. `nextDrawable` is 44,000. It makes a new `CAMetalDrawable` each time, with an `IOSurfaceSharedEvent` that takes a call into the kernel. Making the render command encoder is 36,000, inside the GPU driver. `presentDrawable:` and `commit` are 24,000, and the three draw calls with their state 12,000. Messages go through `objc_msgSend` with selectors registered once at start (`sels` in `objc_darwin.odin`); looking each one up with `sel_registerName` cost about 400 instructions a message, 14,000 a frame.

The shell adds about 40,000 around `app_frame`. Of that, moving the run loop timer for `wake_after` is 20,000 when the frame asks for one (see docs/redraw.md), reading the window for `Frame_Input` is 7,000, and the autorelease pool is 2,500. Waking the main thread and the run loop's pass around the frame, in AppKit, Core Animation and the kernel, is about 100,000 more.

The other threads are Metal and Core Animation. Submitting the command buffer costs them about 290,000 and presenting the drawable about 360,000, found by running frames with no present and with no command buffer at all. Presenting includes Core Animation's callbacks for when the drawable was shown and composited, and macOS 26's FramePacing and Metal HUD bookkeeping (macOS loads `libMetalMetricsInterpose.dylib` into this app, though not into Finder). None of it moved with the layer's settings. The layer is already opaque, and a nil colorspace, `displaySyncEnabled = NO` or calling `present` on the drawable after `commit` changed nothing outside the noise. Colour matching from sRGB to the display happens in the WindowServer, not in the app. A dispatch timer on the main queue is 800 instructions to set instead of 18,000, but it fires on a libdispatch thread and the process total didn't change.
