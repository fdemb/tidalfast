# Windows

The Windows build is a first pass. It runs the same app as macOS and Linux: a Win32 shell in C (`shell/shell_win32.c`), a Direct3D 11 renderer, FreeType text, playback through WASAPI's shared mode, bit-perfect output through its exclusive mode, and the login in the Credential Manager. It is built for x86-64 Windows 10 and 11, on Windows itself with `build.py`, and CI builds and tests it on every push.

## Building on Windows

`python build.py` builds from a prompt with MSVC's `cl`, `lib`, `link` and `rc` on `PATH` (an x64 Native Tools Command Prompt), with `odin` and Python 3 on `PATH` too. `curl` and `tar` come with Windows. With `fxc` from the Windows SDK on `PATH` (`%WindowsSdkBinPath%%WindowsSDKVersion%x64` in that prompt), it compiles the shaders in `src/render/shaders/rect.hlsl` into `src/render/shaders/dxbc`; without it, it uses the bytecode checked in there. Run it with `fxc` after changing `rect.hlsl`, and commit the bytecode.

```
python build.py           debug build\windows\tidalfast.exe, with a console for the log
python build.py release   optimized, the windows subsystem
python build.py dist      release build in build\dist: tidalfast.exe and a .zip of it
python build.py measure   build\measure\: the measure app, mock_tidal.exe and measure.exe
python build.py libs      only the C libraries
python build.py test      the C libraries, then odin test tests
```

The C code is compiled as C11 (`/std:c11 /experimental:c11atomics`). Odin links with MSVC's `link` (`-linker:msvc`): Odin's own rad-link, its default on Windows, has failed here without a message or an exit code. The tests pass on Windows too. Two of them skip what Windows can't do: the time zone comes from the system, not `TZ`, and a variable set to "" is deleted (`tests/os_quirks_*.odin`).

Some things about Odin on Windows that the tools work around: `os.process_wait` reports `success` whatever the exit code, so check `exit_code`; `os.create` makes handles a child process doesn't inherit, so a log handed to a child is opened with `.Inheritable`; and `os.process_terminate` sends a console Ctrl-C, which reaches every process on the console, the one that started it too, so `tools/measure` closes the app's window instead (`stop_windows`).

The C libraries are compiled with `cl` into `build/windows`, apart from the macOS and Linux ones in `build`. `third_party`'s bindings pick `build/windows/<name>/<name>.lib` on Windows. FreeType 2.13.3 comes from its release, checked against its SHA-256, and is built with only the modules the app uses (`third_party/freetype/tf_ftmodule.h`): TrueType and CFF outlines, the SFNT tables with CBDT colour bitmaps and variations, and the anti-aliasing rasterizer. Its zlib and OT-SVG options are off (`tf_ftoption.h`).

`packaging/windows` has the icon, the version resource and the manifest, which `rc` compiles into the executable. The manifest asks for per-monitor DPI awareness (v2) and UTF-8 as the process's code page.

## What's different

- **The shell.** The window is a plain `WS_OVERLAPPEDWINDOW` with the system's title bar, dark where Windows 10 20H1 and later let a window ask. The main loop waits in `MsgWaitForMultipleObjectsEx` on messages, an auto-reset event `request_redraw` sets from any thread, and two waitable timers: the app's `wake_after` and the test driver. A frame draws once for everything that arrived. While the app animates, a frame is drawn as soon as the last one is done, and the blocking present (see Rendering) paces it to the display. A minimized window doesn't animate, since its present doesn't wait and animating would spin, but it still draws the frames asked for, since the app does its work in frames: the queue moves on to the next track in one, and an expired stream URL is fetched again in one. While a drag resizes the window or the system menu is open, Windows runs its own loop, and a timer does the main loop's work from inside it: the frames asked for, `wake_after` and the test steps. A frame can't be re-entered: a message that comes while the app is inside one, as an input method's answer to the shell can, queues its events for the next frame. Sizes are in points of 96 DPI, and `WM_DPICHANGED` moves the window to the size Windows suggests.
- **The shared shell code.** `shell/common.c` has what the Linux and Windows shells share: the event queue, the mirror of the focused text field, the accessibility tree kept for tests, the Now Playing log and the test driver. Each shell adds its own test steps through `os_test_step`.
- **Keys and text.** Letters and digits are mapped by the virtual key the layout gives them, as Windows apps' shortcuts are: Control+Z is undo on the key labelled Z on a German QWERTZ or a French AZERTY keyboard, and on Dvorak, and since a Cyrillic or Greek layout gives its letter keys the US letters' virtual keys, Control+C still copies there. Editing and navigation keys come from their virtual keys too, which the keypad's keys share with NumLock off. The rest go by scan code, the key's place on the keyboard, as evdev codes do on Linux: the key under Escape is the overlay's backtick whatever it types. macOS and Linux map every key by place. Alt+F4 and Alt+Space stay the system's. While a text field has the focus, a key that types something comes as text from `WM_CHAR`, surrogate pairs joined. An input method composes through IMM32: its composition string is marked text with the input method's caret, its result string is inserted, and its candidate window goes under the caret the app reports. The app draws the composition itself. The window has an input method context only while a text field has the focus (`ImmAssociateContextEx`), so a CJK input method is off elsewhere and Space reaches play and pause instead of the input method. When the app ends a composition itself, the shell completes it for the input method and leaves out the result string that brings, which the field already has. Control is the primary modifier, as on Linux. Only the shared mirror behind the input method is tested (the `mark=` and `commit=` steps); the IMM32 messages themselves haven't met a real input method yet.
- **Pointer and wheel.** `Frame_Input.mouse_buttons` comes from `GetAsyncKeyState`, the buttons held now whichever app gets them, swapped back when the user swapped the left and right buttons. When another window takes the mouse capture in the middle of a drag, as Alt+Tab does, the shell asks for a frame, and the app cancels the buttons that are up by then. A whole wheel notch scrolls the user's "lines per notch" setting. A fraction of a notch, from a precision touchpad or a free-spinning wheel, is a precise scroll in points, 16 to a line. Windows sends touchpad scrolls without phases, so there is no momentum after the fingers lift beyond what the touchpad driver sends. The side buttons and `WM_APPCOMMAND` go back and forward.
- **Media keys.** The media keys reach the app while the window has the focus, as `VK_MEDIA_*` keys or `WM_APPCOMMAND`. Not yet the System Media Transport Controls, which would take them from anywhere and show Now Playing in the volume flyout.
- **Rendering.** `src/render/d3d11_windows.odin` draws what the Vulkan backend draws on Linux, with the same shaders ported to HLSL in `src/render/shaders/rect.hlsl`. It was Vulkan at first, but NVIDIA's Vulkan driver keeps far more private memory than its Direct3D 11 one. A small program that opened an 1100 by 700 window and cleared and presented 60 frames had a private working set of 11 MB with Direct3D 11, 42 MB with Direct3D 12 and 69 MB with Vulkan, on an RTX 3070 Ti (Windows 11 25H2), against 1.2 MB with no graphics at all. In the app, idle on the fake data's library at 1100 by 700 pt, the footprint went from 60.5 MB to 26.5 MB. Direct3D 11 also keeps released objects until the GPU is done with them and orders texture writes with the draws, so the backend has none of Vulkan's staging buffers, fences and barriers. The flip-model swap chain's buffers are BGRA8 with an sRGB render target view over them, so blending is in linear light as on the other backends. A machine without a Direct3D 11 GPU falls back to WARP, Direct3D's CPU rasterizer, and one where even that fails opens the window, draws nothing, logs why and says so in a message box when there's no console. Captures of the library at 820 and 1600 pt, and of the player bar playing, matched the Vulkan build's pixel for pixel, apart from one channel by 1 at the wide size and 10 pixels of the moving progress bar.

  The device needs feature level 11_0, since the shaders are shader model 5; a GPU that only has 10_x gets WARP. A frame's instances are built in an ordinary array and copied into the dynamic instance buffer once, in `end_frame`: the push procs and `backdrop_hash` read instances back, and a `WRITE_DISCARD` mapping is write-combined memory, often uncached, which Microsoft warns is very slow to read. Metal's shared buffers are cached, so reading them there costs nothing.

  The swap chain is the flip model with two buffers, and the device's maximum frame latency is 1 (`IDXGIDevice1::SetMaximumFrameLatency`). `Present(1, {})` blocks until the display takes the frame, so a frame can be one refresh ahead of what's on screen, and that block is what paces animation. The shell draws at once when a frame is due and otherwise waits on messages, the redraw event and the timers. A minimized window's present doesn't wait, which is why it doesn't animate. A system before Windows 10 has no `FLIP_DISCARD`, and the swap chain falls back to `FLIP_SEQUENTIAL`. The swap chain's background, which shows where the buffers don't reach while the window grows, is the sRGB clear colour: the buffers aren't sRGB, so DXGI takes the colour as stored. With `TIDALFAST_D3D_BLT` set, the swap chain is the blt model instead, to tell a fault in the flip path from one in the frames.

  A driver update, a GPU reset (TDR) or a switch to another GPU takes the device away. A present, a swap chain resize or a map that fails then finds the device removed (`GetDeviceRemovedReason`), and `lose` releases everything (`ClearState` and `Flush`, so the old swap chain is gone before a new one is made for the window) and sets `Renderer.device_lost`. The next `begin_frame` makes a new device, and if that fails it tries again every second, on a GPU for the first ten tries, then WARP too, while the app asks for a frame every second. A new device moves `Renderer.device_resets` on, and the app clears the glyph atlas and the cover cache and makes the dev screens' textures again; the glyphs and covers fill again as they're drawn. Music plays on throughout.

  While nobody can see the window, frames aren't drawn. When present says the window is occluded (the screen locked, or the window covered), the next frame only presents with `DXGI_PRESENT_TEST`, and draws if that says it can be seen. While it can't, `Renderer.hidden` stops the app animating, and a frame that wasn't drawn asks for another after 0.25 s, then up to every second, so what changed is drawn soon after the window shows again. An idle window that's covered draws nothing at all. A minimized window draws a frame as it goes, and only the frames the app asks for after that, and the renderer gives back what it doesn't need, as macOS does for a covered window: the swap chain's buffers shrink to a pixel, the backdrop's textures go, and `IDXGIDevice3::Trim` frees what the driver kept. Restoring it makes them again at full size. `TIDALFAST_CAPTURE` keeps drawing at full size in both cases, so a capture still shows the window.

  `Renderer.gpu_ms` comes from timestamp queries around each frame's drawing, read a frame or more later without waiting, so the overlay and `measure frames` show the GPU's time. `TIDALFAST_D3D11_DEBUG=1` turns on the Direct3D debug layer, which comes with Windows' optional Graphics Tools, and logs its messages.
- **Text.** FreeType rasterizes as on Linux (`src/text/fonts_freetype.odin`). The text font is the built-in Noto Sans. Fallback fonts come from a list of the UI fonts Windows 10 and 11 use for each script, in the fonts folder (`fonts_windows.odin`): Segoe UI, Segoe UI Symbol, each script's UI font, and Segoe UI Emoji for emoji. Some of them come in optional font packages, and a font that isn't there is skipped; Nirmala UI is `Nirmala.ttc` on Windows 11 and `Nirmala.ttf` on 10, so both are listed. Checked on Windows 11 25H2 with Hebrew, CJK, Devanagari, Thai, Greek, Arabic and emoji. Coverage is bent by the text's tone before it goes in the atlas, so light text on the dark background isn't heavier than other Windows apps' text (see `docs/text.md`, Draw). LCD (subpixel) text would need dual-source blending and a three-channel atlas, and isn't done. Fonts the user installed aren't searched; DirectWrite's font fallback would find them. Segoe UI Emoji's colour layers (COLRv0) are drawn in colour: FreeType blends them into a BGRA bitmap at the size asked for (`FT_LOAD_COLOR`, then `FT_Render_Glyph`), with the foreground colour white, and a glyph with no layers, such as its check mark, is drawn white. The Windows build's FreeType has no PNG decoder, so a font whose glyphs are only PNG bitmaps (CBDT or sbix, such as Noto Color Emoji) is skipped for the next font in the list.
- **Audio.** `src/audio/bitperfect_windows.odin` plays through WASAPI, one event-driven stream filled by a render thread registered as a "Pro Audio" MMCSS task. With bit-perfect output off the stream is shared mode: 32-bit floats at the track's rate with `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM` and `SRC_DEFAULT_QUALITY`, so Windows resamples them to the engine's mix format and mixes, and the Output menu shows the engine's mix rate and the device's format from the endpoint's properties. A stream stays on the device it opened, so an `IMMNotificationClient` tells the player when the default output changes, and a stream reports when its device goes away; either way the player closes the stream and opens it again on the default output, from the audible position. With bit-perfect output on, the same code opens the default output in exclusive mode at the track's rate in the narrowest signed integer format of at least the track's depth that the device takes (16 in 16, 24 in 24, 24 in 32, 32 in 32). The decoder's floats are its integers over 2^31, so `float_to_pcm` gives the device those integers back exactly. Nothing on the device changes, so there is no device change to undo; the device is the shared mixer's again when the stream closes. A device that refuses the rate or format, or that the user set to forbid exclusive mode, plays through the shared mode with the reason in the Output menu. Odin has no WASAPI bindings, so the few COM interfaces are declared in that file. With fake data on a USB headphone adapter, 8 s of shared-mode playback with a pause in it captured 350,936 frames of the tone with no gap, the paused app used no CPU in 10 s, and the Output menu named the device. On an NVIDIA HDMI output that takes only 48 kHz, a 24/48 track played through the player captured every one of its 384,000 samples unchanged, a 44.1 and a 96 kHz track fell back to the shared mode, and the device's shared format was the same afterwards.
- **Login.** The login is a generic credential in the Credential Manager, target `<service>/auth`, which Windows encrypts with the user's login. One credential holds at most 2560 bytes, so a longer login is split across `<service>/auth`, `<service>/auth#1` and so on. `TIDALFAST_KEYCHAIN` names another service against the mock, as on macOS.
- **Files.** Settings and snapshots go in `%APPDATA%\tidalfast` and caches in `%LOCALAPPDATA%\tidalfast`. The app joins paths with `/`, which Windows takes. The environment variables come first, as `XDG_CONFIG_HOME` does on Linux, so a test can point them elsewhere.
- **Memory.** The footprint is the private working set, what Task Manager's Memory column shows; where Windows doesn't report it (before Windows 10 1809, and Wine), the private bytes or the working set stand in. `sys.page_flags` counts a page as in the working set through `QueryWorkingSetEx`. The memory blocks the shell gives the app are committed with `VirtualAlloc`, which costs nothing until a page is written. `TIDALFAST_MEASURE` marks work as on the other systems; the cycle counters come from `QueryThreadCycleTime`, and there is no instruction count.
- **Quitting.** Ctrl-C in the console and SIGTERM, which `sys.quit` raises for `measure`, quit through the main loop, so the app's shutdown runs, which saves the settings. Closing the window (`WM_CLOSE`) quits the same way, minimized or not. Logging off or shutting down Windows can end the process as soon as `WM_ENDSESSION` returns, so the shell runs the app's shutdown inside it; closing a debug build's console waits for the shutdown in the console's handler. There is no SIGUSR1: the shell's `snapshot` test step asks for a memory snapshot.
- **The log.** A debug build logs to its console. A release build has no console, so started from Explorer or the Start menu it has no stderr, and the app logs to `%LOCALAPPDATA%\tidalfast\tidalfast.log`, the shell's lines included, keeping the last launch's as `tidalfast.old.log` (`src/app/logging_windows.odin`). A release build started from a console with its stderr redirected logs there. An error the app can't start or draw after also shows in a message box when there's no console: the window or the memory blocks failing in the shell, or the renderer or the fonts failing in the app.
- **The clipboard.** Only one window can have it open, and clipboard managers open it for a moment after each change, so the shell tries again for up to 60 ms before giving up, and logs it if it does.
- **Measuring.** `python build.py measure`, then `build\measure\measure.exe all`, runs as on the other systems: the machine comes from the registry, and the mock's login is deleted from the Credential Manager after the runs. Run it in a console of its own (`start /wait cmd /c ...`) when something else shares the console. On a Ryzen 5 7600 with an RTX 3070 Ti, the fake data's tracks were drawn 137 ms after the process started, and the footprint at tracks was 23 MB, 32 MB at its peak; against the mock, 27 MB at tracks and 40 MB at its peak, playing. With Vulkan it was 54 MB at tracks, 70 MB at its peak.
- **Test steps.** The shell test steps are the Linux ones (see `shell/common.c` and `shell_win32.c`), and `move=x,y`, `click=x,y`, `type=text`, `vkey=name` (with `ctrl+`, `alt+` and `shift+`, and the keypad's keys as `kp-home` and so on), `wheel=n`, `touchpad=dy`, `minimize`, `restore` and `endsession` go through the window procedure as Windows' own messages would. `endmenu` closes a menu `vkey=alt+space` opened.
- **The mock.** `tests/mock_tidal` encodes its FLAC files with macOS's `afconvert`, and elsewhere with `tests/dashgen`'s verbatim encoder: lossless, but about as big as the WAV.

## Not done yet

- Packaging: an installer, and code signing. `build.py dist` makes a .zip with only the executable in it.
- Following a new default output while exclusive output plays; it moves at the next track.
- The System Media Transport Controls, for media keys from anywhere and Now Playing.
- UI Automation for screen readers. The app's accessibility tree is there; the shell keeps it only for tests.
- Drawing into the title bar, as on macOS, with `DwmExtendFrameIntoClientArea` and `WM_NCHITTEST` for the drag regions the app already reports.
- DirectWrite font fallback for fonts the user installed, and COLRv1 colour fonts.
- Drag and drop.
- Windows on ARM64. Odin has no `windows_arm64` target yet.
